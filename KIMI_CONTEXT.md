# KIMI_CONTEXT — LiftTeam

Краткий входной документ для работы над репозиторием `yachtsman13/LiftTeam`.
Сначала читать этот файл, затем открывать только документы и код, необходимые для задачи.

## Назначение и стек

LiftTeam — система учёта ремонтов лифтового оборудования, склада радиодеталей,
печатных документов, оплат, оповещений и прав сотрудников.

Основной стек: Python 3.11+, Django 5.1, Django REST Framework, Django Channels,
Bootstrap 5. База данных — SQLite по умолчанию или PostgreSQL. Предусмотрено
развёртывание на Raspberry Pi и в Docker.

## Карта документации

- `README.md` — возможности, запуск, тестирование и основные ограничения.
- `PLAN.md` — принятые решения владельца, открытые вопросы, очередь и история этапов.
  Решения владельца обязательны; закрытые пункты очереди не являются новыми задачами.
- `PROMPT.md` — правила работы над проектом.
- `CHANGELOG.md` — история версий; читать последние записи или искать нужную версию,
  не загружать весь файл без необходимости.
- `TZ.md` — подробное техническое задание; использовать только нужный раздел.
- `DEPLOY.md` — развёртывание и эксплуатация; открывать для инфраструктурных задач.
- `CLAUDE.md` — большой справочный документ; читать только найденные поиском фрагменты.

## Проверки и миграции

1. Сначала запускать тесты, непосредственно относящиеся к изменению.
2. Перед публикацией по возможности выполнить `python manage.py test core`.
3. При изменении моделей создать миграции Django и проверить их содержимое.
4. Не изменять существующие миграции, уже применённые в рабочей среде, без отдельного анализа.
5. Не отправлять изменения при неудачных тестах или непроверенной схеме данных.

## Критические предметные правила

- Складские списания и себестоимость используют партии FIFO; возвраты должны сохранять
  корректную связь с исходными распределениями.
- Заработок мастера рассчитывается от фактической `repair_cost`; на гарантийном ремонте — ноль.
- Доступ определяется должностями и настраиваемыми правами, а не прежними зашитыми ролями.
  Последний полный административный доступ нельзя случайно удалить.
- Модель, исполнение, типовая неисправность, технологическая карта и материалы связаны
  согласно решениям в `PLAN.md`; не перестраивать эти связи без указания владельца.
- Готовность выводится из проверок, а не из отдельного вручную поддерживаемого состояния.
- Автосохранение не добавлять: при обрыве связи оно создаёт ложное ощущение сохранённости.
- Банковское уведомление само по себе не разносит деньги; финансовые операции требуют
  особенно тщательной проверки.
- Номер версии изменять только штатным механизмом проекта, не массовой заменой по файлам.

## Общие правила разработки

1. Вносить минимальные изменения, необходимые для задачи; не делать попутный общий рефакторинг.
2. Сохранять существующую архитектуру, стиль интерфейса и соглашения проекта.
3. Обновлять `PLAN.md`, `CHANGELOG.md`, `README.md` и другую документацию только по существу.
4. Не добавлять `.env`, секреты, токены, `db.sqlite3`, рабочие базы, локальные медиафайлы
   и пользовательские данные.
5. Не использовать force push и не переписывать историю Git.

## Ветка и публикация

Основная ветка — `main`. После успешного завершения и проверки задачи изменения сразу
коммитятся и отправляются в `main` без pull request. Дополнительное подтверждение на обычный
commit и push не требуется. При неудачном push задача не считается полностью завершённой.

## Текущее состояние и возможные задачи

По `PLAN.md` основная очередь была закрыта. Перед началом работы проверять актуальное состояние
кода и документов, не повторяя завершённые этапы.

В документации упоминалась возможная оптимизация списка заказов: отдельные запросы при расчёте
`total_repair_cost` для каждой строки. Это кандидат на отдельную задачу с измерением запросов
и проверкой отсутствия задвоения сумм при фильтрации. Другие задачи выбирать по актуальному
`PLAN.md` или указанию владельца.

## Ограничения облачной проверки

Django-тесты и проверки кода можно выполнять в облаке. Реальные операции с Т-Банком, Точкой,
Яндекс.Диском, Telegram, MAX, Tailscale, Raspberry Pi, камерами, принтерами и сканерами требуют
проверки в живой среде. Не утверждать, что такие интеграции проверены, если выполнялись только
локальные или имитационные тесты.
