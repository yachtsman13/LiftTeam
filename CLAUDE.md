# LiftTeam

Django-приложение для учёта заказов на ремонт лифтового оборудования и склада
радиодеталей. Работает в офисе на Raspberry Pi 4; сотрудники подключаются
локально и через интернет по Tailscale — с компьютеров, планшетов и телефонов.

**Правила работы над проектом — в [PROMPT.md](PROMPT.md). Прочитай его перед
первой правкой. Что делать дальше и что уже решено — в [PLAN.md](PLAN.md).** Здесь только то, что нужно, чтобы запустить проект с нуля;
процесс, соглашения и подводные камни описаны там и намеренно не дублируются.

## Запуск с нуля

База данных в репозиторий не входит (в ней реальные данные заказчиков), так что
свежий клон её не содержит. Развернуть пустую:

```bash
pip install -r requirements.txt
```

```bash
python manage.py migrate
```

```bash
python manage.py init_cells
```

```bash
python manage.py create_admin --username admin --name Administrator --password admin123
```

Эти учётные данные — только для разработки. На рабочей установке администратор
заводится с настоящим паролем по `DEPLOY.md`, и `admin123` там быть не должно.

## Проверка изменений

```bash
python manage.py test
```

Сервер разработки поднимается конфигурацией `lifteam` из `.claude/launch.json`
(порт 8000) — запускай через неё, а не вручную. Вход — теми же учётными
данными, что созданы выше.

## Чего в проекте нет

Это регулярно предполагают по ошибке, а затем строят на пустом месте:

- модели документов (`Document`) и счёта как сущности. Акты приёма,
  выполненных работ и дефектации и коммерческое предложение — это печатные
  формы заказа (шаблоны в `core/templates/core/repair_orders/`), нигде
  не хранятся и своих номеров не имеют; PDF собирает браузер, серверного
  рендеринга нет.
  Счёт — не печатная форма: его создаёт банк по запросу программы,
  и номер к нему задаёт отправитель, а не банк;
- методов, двигающих деньги: `core/tbank.py` читает выписку и выставляет
  счета (`invoice/send`), `core/tochka.py` только выставляет счета, но
  платёжных поручений нет ни там, ни там и быть не должно.
  Счёт создаёт документ, списать по нему деньги банк не даст никому;
- разноса денег по уведомлению банка. Приём уведомлений с v2.52.0
  работает у Т-Банка (см. отдельный раздел ниже), но `Payment`
  из уведомления не создаётся и `payment_status` не меняется: суммы
  в уведомлении Т-Банка нет вовсе. Оплата по-прежнему разносится
  человеком по выписке;
- мессенджеров, кроме MAX и Telegram (`core/messengers.py`) — так было
  до v2.97.0, когда заказчикам уходили только письма, а MAX и Telegram
  были только у сотрудников (дефицит деталей, сводка по задолженностям).
  С v2.97.0 заказчик тоже может получать MAX и Telegram — но только
  через контакты (`ClientContact`, ниже), явно указавшие свой ID
  и включившие канал; сам факт «заказчикам можно писать» решает
  по-прежнему только `NOTIFY_CLIENTS`;
- бухгалтерии как таковой: `Payment` — это только поступившая по заказу
  сумма с датой, без проводок, счетов учёта и НДС;
- размеров ячейки в миллиметрах: `Cabinet` (с v2.37.0) хранит только число
  ячеек в каждом ряду, а размер на экране считается от него — ряд из
  четырёх рисуется крупными ящиками, из шестнадцати мелкими секциями;
- ответственного инженера у **заказа** — есть только автор смены статуса.
  Исполнитель ремонта (с v2.97.0) — другое: это поле стоит у **единицы**
  оборудования (`RepairOrderEquipment.repairer`), не у заказа целиком,
  и не выводится из истории статусов — его выбирают руками в разделе
  «Ремонт» на странице единицы;
- смены владельца оборудования при повторном приёме: `current_client`
  проставляется только пустой и не перезаписывается никогда (решение
  владельца). Приезд от другого обслуживающего предприятия не значит,
  что прибор сменил хозяина, а у кого он был в каждом ремонте, видно
  по заказам;
- поставок и продажи оборудования: коммерческое предложение строится
  из заказа на ремонт, предложений на поставку программа не делает;
- офлайн-режима: с v2.49.0 есть понятная реакция на обрыв связи (полоса
  вверху страницы, удержание POST-форм с сохранением введённого), но нет
  ни кэша страниц и справочных данных для чтения без связи, ни очереди
  действий, отправляемой самой при восстановлении. Второе — намеренный
  отказ: повтор с неясным исходом первой попытки задваивает заказы
  и списания. Service worker в проекте отсутствует.

Настройки читаются **живыми из `.env`** — с v2.86.0, `core/envfile.py`.
Хранилище — сам файл, а не база: ночная выгрузка увозит `db.sqlite3`
в облако, а `.env` не увозит, и токенам банков в том, что уезжает,
не место даже зашифрованными (ключ оказался бы на том же устройстве).
Разбирает файл сам `python-dotenv` — тот же, что читает его при запуске;
второго разбора заводить нельзя, они разошлись бы на кавычках.

Правило главенства одно: **значение из файла главнее только тогда, когда
файл после запуска менялся**. Сравнение — с `os.environ`, куда
`load_dotenv()` положил снимок при старте: имени в файле нет — берётся
настройка Django; в файле то же, что в окружении — берётся настройка;
другое — берётся файл. Отсюда два запрета: **после записи в файл
`os.environ` обновлять нельзя** (сравнение скажет «не менялось»,
и программа продолжит отдавать старое), и `ENV_FILE_PATH` обязан
указывать на тот же файл, что читает `load_dotenv()`. На этом же правиле
держится `override_settings` в тестах у того, у кого рядом лежит свой
`.env`.

Тип значения берётся у настройки из `settings.py` (`_coerce`): там оно
уже разобрано, и описывать тип второй раз не надо. Составные настройки
(`ORDER_OVERDUE_DAYS` собирается из четырёх переменных) читаются
по именам своих переменных.

Читают через `envfile.setting` **все** модули банков, Диска, ботов
и оповещений; `getattr(settings, ...)` для настройки, задаваемой
в `.env`, — это ошибка: правка перестанет действовать до перезапуска.

Секреты (`envfile.SECRET_NAMES`) вводятся **командой у самого Pi** —
`manage.py setsecret ИМЯ`, скрытый ввод с повтором, значение не печатается
и аргументом не принимается (осело бы в истории команд). Из веб-интерфейса
секрет не пишется: `set_value` требует `allow_secrets=True`, и передаёт
его одна эта команда. Причина отказа от веб-формы: страница доступна
с любого устройства Tailscale, а по локальному адресу 192.168.1.x браузер
идёт без сертификата (он выдан на имя в Tailscale) — токен ушёл бы
открытым текстом. Наружу отдаётся только `describe_secret` — «задан,
40 знаков», без значения.

Проверку связи со службами держит **одно место** — `core/selfcheck.py`
(`check(name)` → `CheckResult`): команда и страница настроек обязаны
говорить об одной службе одно и то же. Все проверки читающие, следов
не оставляют. У Точки живой проверки нет намеренно — её документация
недоступна, и угаданный адрес отвечал бы «связи нет» на исправном токене.

У секретов вебхуков проверять связь не с кем: уведомление присылает банк,
а секрет — то, чего мы ждём от него. Поэтому с v2.90.0 проверяется
готовность приёма: включатель, непустой секрет, **его вид** (записанный
без схемы «Bearer » он выглядит заполненным, но не совпадёт ни с одним
уведомлением), список адресов и — главное — сколько уведомлений принято
на самом деле (`WebhookDelivery`). Доставка и есть единственное возможное
подтверждение секрета. У проверяющего есть флаг `verifiable`: у Точки
он ложь, и проверка говорит, что приём откажет при любых настройках, —
рапортовать «настроено верно» о неработающем нельзя.

Чего в живых настройках нет: `SECRET_KEY`, `ALLOWED_HOSTS`,
`CSRF_TRUSTED_ORIGINS`, `DEBUG` — Django читает их один раз при старте;
`EMAIL_HOST_PASSWORD` пишется, но подхватывается только после
перезапуска (его берёт почтовый слой Django мимо `envfile`), и команда
об этом предупреждает; `WEBHOOKS_TBANK_IPS` — те же адреса стоят
в `deploy/nginx-lifteam-hooks.conf`, а nginx в файл настроек не смотрит.
Удаления строк из файла тоже нет: «стереть» означает записать пустое.

Должности с настраиваемыми правами — с v2.98.0, вместо четырёх зашитых
в код ролей (`Employee.role`, удалено). `Position` — справочник
(название, `is_admin`, примечание), `PositionPermission` — отмеченное
у неё право, у `Employee` осталась одна ссылка `position`
(`PROTECT`: удаление занятой должности молча лишило бы людей прав).
Правится в программе — `/management/positions/`, `views.admin_positions`
и три страницы рядом.

Список прав **явный** — `models.PERMISSIONS` (код, название, раздел),
разделы — `PERMISSION_SECTIONS`; заводить право «на лету» из строки
в запросе нельзя, тот же приём, что у `envfile.EDITABLE`
и `UNIT_SECTION_FORMS`. Набор прав — слепок тех проверок, что уже стояли
в коде до v2.98.0, и ни одной новой: перенос обязан был быть
тождественным, а завести новое ограничение под видом миграции — способ
сломать работу людям, ничего им не сказав.

Проверка одна на всю программу — `decorators.permission_required(code)`
(`role_required` больше нет). Полный доступ (`is_admin`) проходит **всё**,
включая права, которых ещё нет: они появятся с версией, а у должности
их никто не отмечал, и раздавать их молча всем нельзя — поэтому
наследование только у полного доступа, у обычной должности его нет.
Отсутствие должности — доступ как у всех, а не как у администратора.

Шаблоны спрашивают через `user.can.<код>` — словарь всех кодов
(`Employee.can`, `cached_property`). Причина именно словаря: шаблонизатор
Django не умеет звать метод с аргументом, а точки в коде права разобрал
бы как обход по атрибутам. Отсюда правило: **коды прав — плоские
идентификаторы через подчёркивание**, `invoices_send`, а не
`invoices.send`. Опечатка в шаблоне ничего не сломает вслух — просто
скроет кнопку, — поэтому за ними следит `PermissionCodesInTemplatesTests`:
он вычитывает `user.can.(\w+)` из всех шаблонов разом и сверяет
с каталогом.

Без полного доступа программа неуправляема, поэтому его последнего
носителя убрать нельзя — ни снятием галочки с должности, ни увольнением,
ни переводом человека. Сторож — `views._admin_access_kept`: правка идёт
в транзакции, и **после** неё спрашивается `models.admin_access_exists()`;
пропало — `LastAdminError` и откат. Предсказывать «что станет истинным
после сохранения» здесь нельзя: способов остаться без администратора
несколько, и перечислять их по одному значит однажды пропустить.
Сторож смотрит на состояние **до** правки тоже: если полного доступа уже
нет (база после ручной правки), он не мешает — иначе чинить было бы
нечем. Починить при этом есть чем: право `admin_access` («управлять
пользователями, должностями, настройками») — не то же самое, что
`is_admin`, и должность с ним одним до страницы должностей доходит.

Заводские должности создаёт миграция `0051`, и **все четыре, даже
пустые**: это стартовый набор, как ячейки у `init_cells`. Значения прав
у них перечислены в самой миграции (`FACTORY_POSITIONS`) и правятся
только вместе с переносом — это снимок прошлого, а не действующая
настройка.

Получателей оповещений выбирает **право**, а не роль
(`notifications._staff(permission)`, константы `STOCK_PERMISSION`,
`DEBT_PERMISSION`, `ORDER_OVERDUE_PERMISSION`, `PAYMENT_PERMISSION`).
Полный доступ получает всё (`Q(position__is_admin=True) |
Q(position__permissions__code=...)`, и `.distinct()` обязателен —
соединение по правам двоит строки).

Оповещение о новом поступлении (`notify_new_payment`, право
`notify_payments`, с v2.103.0) зовётся из `tbank.fetch_and_store` —
того же общего места, что и у команды по расписанию, и у кнопки
«Загрузить сейчас» — один раз на каждую **новую** строку выписки, без
кулдауна: в отличие от дефицита детали, одна операция создаётся ровно
один раз (`get_or_create` по `external_id`), и оповещать о ней повторно
неоткуда. Само поступление письмом не разносится — оно только
подсказывает зайти на «Поступления» и разнести руками, как и раньше.

Страница «Настройки» — с v2.87.0 (`views.admin_settings`,
`/management/settings/`, только администратору). Правит то, и только то,
что перечислено в `envfile.EDITABLE`: список **явный**, а не «всё, что
не секрет», и `set_value` без `allow_secrets` откажет незнакомому имени —
подсунуть в запрос можно что угодно. Секреты на ней **видны состоянием
и не правятся**; у каждого кнопка «Проверить» (`selfcheck.check` через
`views.admin_settings_check`, ответ JSON, запрос через `LiftTeamWS.fetch`).

Каждый из восьми разделов — своя форма и своя кнопка «Сохранить»
(с v2.101.0), а не одна форма на всю страницу: правка «Т-Банка» не должна
ждать, пока сохранят «Оповещения» в соседней вкладке. Второй код на это
не понадобился — `admin_settings_save` и раньше писал только то, что
пришло в запросе, `if name not in request.POST: continue`, поэтому форма
меньшего размера просто ничего не говорит о полях вне себя.

Флажки шлют рядом скрытое поле `flag` со своим именем, и представление
считает «нет» только для перечисленных в нём: снятая галочка в запрос
не попадает вовсе, и без этого списка неполный запрос молча выключил бы
все оповещения.

Журнал правок — `SettingChange` (имя, кто, когда). **Значения в нём нет
намеренно**: копия значений в базе уехала бы в облако вместе с ней,
а для разбора «после чьей правки сломалось» довольно имени и времени.

Перезапуск службы из интерфейса — с v2.88.0, `core/restarter.py`.
Приём тот же, что у обновления: приложение пишет файл-заявку
(`.restart-request`), а перезапускает служба systemd от root
(`deploy/lifteam-restart.{path,service}`, скрипт —
`/usr/local/sbin/lifteam-restart`, вне каталога приложения и от root:
рядом с кодом его подменил бы взломщик). Отличие от обновления в том,
что **из заявки ничего не читается** — скрипту нужен один факт «файл
появился», и подставить в него нечего в принципе. Заявка удаляется
скриптом **до** `systemctl restart`: перезапуск обрывает и сам скрипт,
а оставленный файл увёл бы приложение в бесконечный перезапуск.
Нет скрипта — `restarter.is_available()` ложь, и страница говорит,
что перезапуск не настроен, вместо того чтобы обещать несбыточное.
Своего слежения за ходом перезапуска нет и не надо: обрыв и возврат
связи показывает обычная полоса вверху страницы.

«Нужен перезапуск» **не хранится, а выводится** — `envfile.restart_needed()`:
настройка помечена `restart` и в файле лежит не то, что было при старте.
После перезапуска снимок совпадёт с файлом, и список опустеет сам. Флаг
пришлось бы гасить руками, и он начал бы врать — то же правило, что
у готовности единицы оборудования.

`ALLOWED_HOSTS` правится страницей, но **свой адрес из списка вычеркнуть
нельзя** (`views._keep_current_host`): это единственная настройка, ошибка
в которой закрывает программу целиком — Django ответил бы «400 Bad
Request» на всё, и чинить пришлось бы по SSH. Адрес возвращается молча,
а сказано об этом вслух; убрать его можно, открыв программу по другому
адресу из списка. `DEBUG` на страницу не вынесен намеренно: включённый,
он показывает в браузере устройство программы вместе с настройками.

Списочные настройки (`ALLOWED_HOSTS`, `CSRF_TRUSTED_ORIGINS`) в поле
ввода рисуются строкой через запятую — `envfile.as_text`, зовётся
из `describe_editable`. Без него в поле попал бы список Python,
а оттуда обратно в файл, и при следующем запуске скобки с кавычками
стали бы частью адреса.

Частоту загрузки выписки Т-Банка решает **программа, а не расписание**
(с v2.89.0). Таймер `deploy/lifteam-tbank.timer` только тикает — раз
в четверть часа в рабочее время, — а тянуть ли выписку на этом тике,
отвечает `tbank.fetch_due()` по настройке `TBANK_STATEMENT_INTERVAL_MINUTES`
со страницы настроек. Причина разделения: юнит systemd правится от root,
и владелец его не поправит. Юнит зовёт команду с `--scheduled`; без этого
флага промежуток не спрашивается вовсе — человек, набравший команду
руками, хочет выписку сейчас.

Отметка о последней загрузке — **файл** `.tbank-last-run`
(`tbank.LAST_FETCH_FILE`), не строка в базе: это состояние установки,
а не данные, и в базе оно уехало бы в облачную копию и после
восстановления соврало бы, что выписку только что тянули. Ставится
**после** удачной загрузки: сорвись запрос к банку, следующий тик обязан
попробовать снова. `--dry-run` её не двигает.

Само чтение и сохранение выписки — **одно место**, `tbank.fetch_and_store`
(с v2.99.0): его зовёт и команда без `--dry-run`, и кнопка «Загрузить
выписку сейчас» на странице «Поступления» (`views.bank_statement_fetch`).
Второй такой код разошёлся бы с первым, а склад денег — не то место,
где это можно позволить. Кнопка, как и ручной запуск команды, промежуток
не спрашивает — нажавший хочет выписку сейчас; отметка времени и текст
«Последняя загрузка: …» рядом с кнопкой читают тот же `last_fetch_at()`,
что и команда.

Живые приписки под полями настроек (`envfile.describe_editable(name, note)`,
`editable_sections(notes)`) считает **представление** — `views._settings_notes`:
`envfile` не должен знать ни про банк, ни про Диск. Привязка идёт
по **имени настройки**, а не по названию раздела: имя — опознавательный
знак, названия разделов переписывают.

Приём уведомлений от банков — с v2.51.0, и с v2.52.0 у Т-Банка он
работает. Устройство: два адреса (`/webhooks/tbank/`, `/webhooks/tochka/`)
в отдельном наборе маршрутов `core/webhook_urls.py`, представление
`core/webhook_views.py`, проверяющие и разбор в `core/webhooks.py`,
запись доставки — `WebhookDelivery`.

**Подписи у Т-Банка нет вовсе** — это свойство его вебхуков, а не наш
пробел, и искать её в документации больше не надо. Подлинность держится
на двух условиях, и оба обязательны: адрес отправителя из шести
документированных (`WEBHOOKS_TBANK_IPS`) **и** совпадение заголовка
`Authorization` с `WEBHOOKS_TBANK_SECRET` — секрет придумывает владелец
и сообщает банку письмом. Пустой секрет означает отказ: один список
адресов слишком слаб, чтобы остаться единственной проверкой. Сравнение —
`hmac.compare_digest`. За обратным прокси настоящий адрес считает
`webhooks.client_address`: последнее звено `X-Forwarded-For`, и только
если `REMOTE_ADDR` входит в `WEBHOOKS_TRUSTED_PROXIES`. Те же шесть
адресов перечислены в `deploy/nginx-lifteam-hooks.conf`; расходиться
списки не должны, за этим следит `WebhookTBankAddressListTests`.

Принимается **одно** событие — «Обновление статуса счета на оплату»
(`{"invoiceId": ..., "status": "PAID"}`). Событие «Операция по счету»
не принимается намеренно: связать операцию выписки с заказом можно
только гаданием, а выписку разносит человек. Найденному заказу
проставляется `invoice_paid_at` и ставится оповещение бухгалтерии;
`Payment` не создаётся, `payment_status` не меняется — суммы
в уведомлении нет. Не найден счёт — доставка получает состояние
`unmatched`, и банку всё равно отвечается 200: он повторяет доставку
при любом не-2XX, а повторять тут нечего. Ключ повтора — `invoiceId`.

Чего в приёме нет: у Точки не написано ничего и писать не из чего —
её документация об уведомлениях недоступна, её проверяющий отказывает
всегда и называет недостающее. Не подтверждено и имя поля, из которого
берётся `invoice_external_id` в ответе Т-Банка на выставление счёта
(`tbank.invoice_external_id`): читаются несколько правдоподобных имён,
принимается только значение вида UUID. Без него уведомление заказ
не найдёт — это единственное звено цепочки, проверяемое только на живом
счёте.

Под префиксом `/webhooks/` не должно оказаться ничего постороннего:
на Raspberry Pi nginx открывает в интернет ровно этот префикс и отвечает
404 на остальное (DEPLOY.md, раздел «Приём уведомлений от банков
из интернета»), так что случайный сосед под этим префиксом стал бы
доступен миру. За этим следит `WebhookUrlIsolationTests`.

Приложение целиком от интернета закрывает не `server_name`, а
`allow`/`deny all` по адресу отправителя в `deploy/nginx-lifteam.conf`:
заголовок `Host` подставляет кто угодно, и nginx выбирает блок по одному
только ему. До v2.52.0 там стоял `server_name _;`, который перестал
совпадать с чем-либо, как только блок уведомлений стал `default_server`, —
и приложение переставало открываться через nginx вовсе.

Состояние связи считает `core/static/js/ws-connection.js` — он же держит
сокеты; полоса и удержание форм — `core/static/js/connection-status.js`.
Отдельного опроса сервера «жив ли он» нет и заводить не надо: присутствие
держит сокет на каждой странице. Ответ сервера с ошибкой (4xx/5xx) обрывом
связи не считается. Полоса прячется атрибутом `hidden` и правилом в стилях
`base.html`, а не классом `d-none`: Bootstrap грузится из интернета и при
неполадках со связью может не приехать — то есть ровно тогда, когда полоса
и нужна.

WebSocket с v2.20.0 работает целиком: браузер подключается к `ws/stock/`
на страницах с остатками (`core/static/js/stock-updates.js`) и обновляет
цифры на месте. Раньше клиентской части не было вовсе. С v2.48.0 каналов
два: к остаткам добавилось присутствие сотрудников (`ws/presence/`), и оно
подключается на **каждой** странице. Логика переподключения после обрыва
общая — `core/static/js/ws-connection.js`; дублировать её в новых скриптах
не надо.

Присутствие — с v2.48.0. Отдельной модели нет: это поле `Employee.last_seen`
плюс настройка `PRESENCE_TIMEOUT_SECONDS` (90 с), а «в сети» — свойство
`Employee.is_online`, то есть чистая функция от них двоих. Флага «онлайн»
нет намеренно: его пришлось бы гасить при разрыве, а разрыв неотличим
от заминки в сети. По той же причине `disconnect()` отметку **не** трогает,
и закрывший браузер числится в сети до конца таймаута — это не баг.
Чего в присутствии нет: привязки к терминалу (идентичности рабочих мест
в проекте не существует вообще — ждёт авторизации по NFC), серверных
таймеров и опроса по расписанию (список рассылается на подключение,
на сигнал от браузера и на отключение — этого достаточно, потому что
сигнал шлёт каждый подключённый), а также истории присутствия: хранится
только последняя отметка, журнала «кто когда был» нет.

Выбор типовых неисправностей — с v2.82.0 выпадающий список плюс кнопка
«Добавить» (`core/templates/core/_fault_picker.html`,
`core/static/js/fault-picker.js`). Списка с множественным выбором больше
нет: на планшете он почти неработоспособен, а при десятке неисправностей
не видно, что выбрано. Наружу уходят те же скрытые поля под прежним
именем, поэтому представления и проверки не менялись — приём тот же, что
у выбора детали. Выбранные рисует **сервер**, скрипт лишь прячет их
в списке; сложность помечена цветом там же.

Многострочные поля растут по содержимому — `core/static/js/autogrow.js`,
подключён в `base.html`, находит поля сам: править формы не надо.
Высота меряется от `height: 0`, а не от `auto`: при `auto` текстовое поле
принимает высоту из атрибута `rows`, и поле с `rows="3"` так и остаётся
в три строки при одной строке текста. Выше `MAX_ROWS` (12) не растёт.

Детали единицы правятся **на её странице** (с v2.82.0): форма списания
там же, единицу выбирать не надо. Форма на карточке заказа тоже осталась,
но с v2.96.0 она **тоже требует назвать прибор** — «на заказ целиком»
больше не выбирают (решение владельца), и списывать «в заказ вообще»
теперь негде намеренно: по такой записи не посчитать, во сколько обошёлся
ремонт каждого прибора. Возврат после действия — `next` в POST
через `views._back_after_detail`, адрес проверяется
`url_has_allowed_host_and_scheme`.

Выбор детали — с v2.53.0 один на всю программу и **обязателен везде**,
где указывают одну деталь: обычный `<select>` по каталогу больше не
рисуется нигде и заводить его заново не надо (за этим следит
`PartPickerEverywhereTests`). Устройство: вставка шаблона
`core/templates/core/_part_picker.html`, поведение —
`core/static/js/part-picker.js`, вид — `core/static/css/part-picker.css`
(оба подключены в `base.html` на каждой странице), поиск на сервере —
`views.part_search` (`/parts/search/`). Новое место выбора — одна вставка,
без правки скриптов.

Наружу выбор отдаёт **скрытое поле с номером детали под прежним именем**,
поэтому принимающие представления и формы при переходе не менялись и
менять их не нужно. Отбор — тот же `views._filter_parts`, что у списка
радиодеталей, выгрузки и печати пачки этикеток (он принимает словарь
параметров, а не запрос); второго набора условий заводить нельзя — «найдено
3» на складе и то, что предлагает выбор детали, обязаны совпадать.
В строке результата, кроме артикула и названия, обязательны остаток
и адрес ячейки: по ним решают, идти к полке или заказывать. Отдаётся
не больше `views.PART_SEARCH_LIMIT` (50) строк, и ответ прямо говорит,
что показано не всё (`limited`, `total`).

Два условия, оба нарушать нельзя: **никакого Bootstrap JS** (ни
`data-bs-*`, ни `modal` — Bootstrap приходит из интернета; панель прячется
атрибутом `hidden`) и запросы **только через `LiftTeamWS.fetch`**, иначе
обрыв связи выглядит как «ничего не найдено» вместо общей полосы вверху
страницы. Обработчики повешены на документ, а не на каждую разметку:
строки рецепта неисправности размножаются копированием готовой строки,
и выбор в копии обязан работать сам (копия при этом чистится вызовом
`LiftTeamPartPicker.reset`).

Чего в выборе нет: множественного выбора (везде выбирается ровно одна
деталь), заведения новой детали прямо из него и подсказок «недавно
выбранные» — истории выбора программа не хранит.

У типовой неисправности **два текста для документов, и путать их
нельзя** (второй — с v2.81.0): `description` отвечает «что нашли»
и печатается в акте дефектации и в предложении, `work_description` —
«что делают», и подставляется в поле выполненных работ. Акт выполненных
работ с фразой «конденсаторы потеряли ёмкость» читается как отчёт о том,
что ничего не делали.

Подставляет **кнопка**, а не программа сама: неисправности выбирают при
дефектации, до ремонта, и автоматическая сборка акта показала бы «работы
записаны» по неразобранному прибору — то же правило, что у цены из прайса.
Сборка — `RepairOrderEquipment.typical_work_lines` (и `typical_work_json`
для разметки), поведение кнопки — общий
`core/static/js/typical-work.js`, подключённый в `base.html`: новое
место — кнопка с `data-typical-work`, `data-target`, `data-lines`,
без правки скрипта. Набранное руками не затирается, повторное нажатие
не задваивает, и каждый исход назван вслух. Стоит на странице единицы
(выполненные работы) и в форме предложения (предлагаемые).

Короткое название типовой неисправности (`FaultType.name`) в документы
не попадает **никогда** — это правило, а не умолчание. В акт дефектации
и в коммерческое предложение идёт только `FaultType.description`, полная
формулировка; неисправность с пустым описанием не даёт в документ ничего,
и подставлять вместо описания название нельзя. Текст для документа
собирает одно место — `RepairOrderEquipment.document_fault_text` (и его
обёртки `diagnosis_document_text` для акта и `quote_line` для
предложения): сначала описания выбранных неисправностей, потом свободный
текст мастера. Разводить эту сборку по печатным шаблонам не надо —
заказчик не должен получить в одном документе описание, а в другом
цеховой жаргон. Заказ без выбранных типовых неисправностей печатается
ровно как до v2.54.0, и за этим следит `FaultTextInDocumentsTests`.

Сложность ремонта с v2.54.0 живёт у неисправности (`FaultType.complexity`,
простой/сложный): она свойство вида поломки, а не прибора. У единицы
в заказе остаётся прежнее правимое поле `repair_complexity` — **тоже
простой/сложный, с v2.83.0**: «среднего» ремонта не бывает (решение
владельца), и наборы значений у единицы и у неисправности обязаны
совпадать — из вторых выводятся первые. Пустое означает не «простой»,
а «не задавали», и тогда сложность выводится из выбранных неисправностей: сложна хотя бы одна —
сложен весь ремонт (`derived_complexity`, `effective_complexity`,
`complexity_is_derived`). В предложение печатается `effective_complexity`.

Правится сложность **на странице единицы**, рядом с выбором
неисправностей, из которых она выводится (с v2.84.0; до этого поле
стояло только в форме предложения — то есть нигде, пока предложение
не понадобится, и цвет в списке единиц не появлялся ни у одной строки).
Пустой вариант в списке назван «По неисправностям», а не
«---------»: разница между «простой» и «не задавали» — это разница
между записанным решением мастера и подсчётом по неисправностям,
и молчаливое «---------» о ней не говорит.

В списке единиц заказа сложность **своего столбца не имеет** (с v2.85.0):
он слит со стоимостью — в ячейке фактическая `repair_cost`, сложность
несёт цвет значка, а слово показывается, только пока цифры нет. Что
окажется в ячейке, решает одно место — `RepairOrderEquipment.cost_cell`
(`{'text', 'css', 'muted'}`), а не цепочка условий в шаблоне: на телефоне
та же строка рисуется карточкой, и разойтись двум видам нельзя. Оценка
из дефектации в этот столбец не идёт (решение владельца), у гарантийного
ремонта без стоимости написано «по гарантии», а не прочерк.

Заработок исполнителя (`RepairOrderEquipment.earnings`, с v2.97.0) —
той же логикой, что и стоимость в ячейке: фактический `repair_cost`,
а не оценка из дефектации, и `None`, пока стоимость не проставлена
(«не заработал» и «ещё не посчитано» — разные вещи, как и у
`cost_cell`). На гарантийном ремонте — **ноль**, а не сама стоимость
и не пусто: денег с заказчика нет, но врать, что заработка не бывает
вовсе, тоже не дело. Кто исполнитель, правится рядом, в разделе
«Ремонт» на странице единицы (`repairer`, `SET_NULL` на Employee —
уволенный мастер не должен утаскивать за собой запись о ремонте).
Отчёта по заработку за период программа не строит — эта цифра видна
только на странице конкретной единицы.

Контактные лица заказчика (`ClientContact`, с v2.97.0) — таблица
на странице заказчика (формсет, тем же приёмом, что материалы модели:
только у уже сохранённого заказчика, вешать контакты не на что раньше).
У каждого — телефон, почта, ID в MAX, ID в Telegram и три галочки
(`notify_by_email`/`notify_by_max`/`notify_by_telegram`), тот же приём,
что у `Employee.notify_by_*`. Поля `Client.contact_person`/`phone`/
`email` никуда не делись — это резервный канал для заказчика,
у которого контактов ещё не завели.

Рассылку собирает одно место — `notifications._queue_to_client`:
контактов нет — письмо, как и раньше, уходит на `Client.email` одним
адресом; контакты есть — общий `Client.email` в рассылке больше **не
участвует вовсе**, письмо уходит каждому контакту по включённым у него
каналам. И `notify_order_status`, и `notify_debt` зовут это место, а не
свою версию — второй такой код разошёлся бы с первым. Канал MAX/Telegram
молчит, если сам мессенджер не настроен (`messengers.max_is_configured()`)
— отправлять было бы всё равно нечем, а очередь заполнилась бы
сообщениями, которые никогда не уйдут.

Цвет сложности считает **одно место** — `models.complexity_css`
(и обёртки `FaultType.complexity_css`,
`RepairOrderEquipment.effective_complexity_css`): зелёный простой,
красный сложный, пусто — без цвета. Цепочек `{% if %}` по шаблонам
не заводить: так уже разъехались статусы заказа, у которых условия
переписаны отдельно в списке и на карточке. **В печатных формах цвета
нет** — на бумаге он уходит в серый.

Общего описания неисправности у заказа нет с v2.83.0
(`RepairOrder.fault_description` удалено): его заполняли вместо описания
по прибору, то есть спрашивали одно и то же дважды, и ни в одном заказе
владельца оно заполнено не было. Неисправность записывается у единицы.
Миграция `0047` перед удалением столбца переложила непустой текст в те
единицы, у которых своего описания нет, — ровно так его и печатал акт
приёма.

В выборе исполнения на карточке оборудования — только исполнения
выбранной модели (с v2.80.0; данные берутся из `ajax_equipment_model_list`,
того же источника, что у окна заведения при приёме). Смена модели снимает
выбранное исполнение и говорит об этом строкой: к новой модели оно
не относится. Отбор в браузере — удобство, последнее слово за `clean()`
формы.

Дата акта дефектации проставляется сама в день первой записи
(`stamp_defect_act_date`, зовётся из `repair_order_defect_act_edit`)
и дальше не двигается; правится руками. До v2.80.0 пустая дата означала
«печатай сегодняшнее число», и акт, заполненный в понедельник, к среде
становился средой. У актов, заполненных раньше, дата пустая: у строки
заказа нет ни одной отметки о времени, и взять её неоткуда.

Типы оборудования и версии моделей — с v2.54.0. `EquipmentType` —
справочник («Привод дверей», «Преобразователь частоты»), ссылка на него
стоит у **модели**, а не у единицы: любой EkoDrive 2.0 — преобразователь
частоты. Тип **не заменяет** `EquipmentModel.kind` и с ним не сливается:
`kind` — это приставка к названию модели в акте дефектации, которую
оставляют пустой, если родовое слово уже стоит в названии («Преобразователь
частоты Emotron»); подстановка типа в акт напечатала бы его дважды. Тип
в документы не идёт вовсе, он нужен прайсу заказчика (следующий этап).

`EquipmentVersion` — исполнение модели (EkoDrive 2.0-1.1 и 2.0-0.7)
с комментарием («алюминиевый корпус»). У единицы версия и дата
изготовления необязательны, у модели тип необязателен — пусто у всего,
что заведено раньше, и миграция ничего не выдумывает.

**Обозначение версии печатается везде** — в акте приёма, акте дефектации,
акте выполненных работ, на этикетке и в списках выбора. До v2.58.0 было
ровно наоборот («ни в один документ не идут»); владелец решение изменил:
одна и та же модель в разных исполнениях — разное изделие, и в документе
это должно быть видно.

Форма — **слитная приписка**, одной строкой и одним шрифтом:
`БУАД-7-31.4`, `EcoDrive-2.3-1.1`. **Разделитель хранится внутри
обозначения версии** (`.4`, `-1.1`, а у части изделий пробел — ` 21.01`),
склейка — простое сложение строк. Пробел слева выживает только потому,
что `EquipmentVersionForm` ставит полю `strip = False`: Django обрезает
пробелы по краям сам, и до v2.80.0 « 21.01» ложилось в базу как «21.01»,
а печаталось «МАГНУС21.01». Пробел справа форма не принимает — слева
он разделитель, справа опечатка. Невидимый знак показывает живая строка
«Напечатается: …» в карточке исполнения.
Отдельного поля «разделитель» нет намеренно: на изделиях разделители
произвольные, правилом их не вывести, и такое поле заполняли бы руками
при каждой версии — тот же труд, только в двух местах.

Складывается обозначение **простым сложением строк, без своего
разделителя**: он уже внутри обозначения версии. `EquipmentVersion.__str__`
подчиняется тому же правилу — пока дефис был прошит в нём, к нему
добавлялся ещё один из обозначения, и в списке выбора выходило
«БУАД-7-31-.4».

Собирают обозначение два места, и разводить их по шаблонам не надо:
`Equipment.designation` (`БУАД-7-31.4`) — акт приёма, акт выполненных
работ, этикетка, `__str__` в списках; `Equipment.full_designation`
(`Привод дверей БУАД-7-31.4`) — акт дефектации и, с v2.74.0, строка
коммерческого предложения: их читает один и тот же человек, и изделие
в них обязано называться одинаково. Родового слова на этикетке нет намеренно: оно съело
бы место на 43 мм.

**Комментарий к версии (`note`) не печатается нигде** — это по-прежнему
так: «алюминиевый корпус» нужен мастеру у стола, а не заказчику.
Версии нет — не печатается ничего, «исп. 1.0» вместо пустого поля
не выдумывается. За тем и другим следит `EquipmentVersionInDocumentsTests`.

В коммерческом предложении с v2.74.0 изделие есть: первой строкой
колонки «наименование», работы под ним. Собирает
`RepairOrderEquipment.quote_equipment_name` — одно место, как и текст
неисправности. Название **правится руками**
(`RepairOrderEquipment.quote_designation`, пусто — печатается своё):
у преобразователей частоты исполнения отличаются мощностью, то есть
и ценой ремонта, а у приводов дверей почти нет, и что из этого важно
заказчику, решает мастер. В подсказке к полю стоит то, что напечатается
при пустом значении.

Яндекс.Диск — с v2.72.0, и **только папка**: `core/yadisk.py` заводит
`LiftTeam/Заказы/<номер заказа>/<обозначение прибора> SN <серийный номер>`
и записывает ссылку в `RepairOrderEquipment.yandex_disk_folder`. Путь
считает одно место (`yadisk.unit_path`); разойдись он между кнопкой
и проверкой — снимки одного ремонта уехали бы в папку другого. В имени
с v2.93.0 не голый серийник, а обозначение рядом с ним — иначе на Диске
не видно, к какому прибору папка относится (одинаковые кассетницы разных
приборов отличаются подчас одной цифрой в номере).

Ссылку на странице единицы **ставит кнопка**, а не поле ввода
(с v2.93.0). Ручной ввод — своя мини-форма за `<details>` («Указать путь
вручную» / «Изменить путь»): без своего JS, без Bootstrap-модалки,
и ничего на Диске не создаёт — только переопределяет ссылку на случай,
когда папку завели раньше программы или снимки переложили
(`UnitDiskFolderForm`, `views.repair_order_unit_disk_folder_set`).

**На живом Диске не проверено ничего**: сайт документации Яндекса
из среды разработки недоступен, схема запросов написана по памяти
об их REST API. Порядок тот же, что у Точки: код обвешан проверками
и понятными отказами, а первое обращение к настоящему Диску должно
пройти под присмотром. Что считается верным, перечислено в шапке модуля;
обмен целиком прогнан против поднятой рядом заглушки.

Заголовок — `Authorization: OAuth <токен>`, **не Bearer**: у Диска свой,
и с Bearer он отвечает 401. Родительские папки Диск сам не заводит, путь
создаётся по одному уровню сверху вниз; 409 означает «уже есть» и ошибкой
не считается. Запрещённые в имени знаки (косая черта и прочее)
заменяются подчёркиванием, а не выбрасываются: из «SN/12» и «SN12» вышли
бы одинаковые имена.

Чего в Диске нет и не заводить: **загрузки файлов** (снимки кладут
телефоном, программа даёт папку), **публикации наружу** (публичную ссылку
открыл бы кто угодно, а внутри оборудование заказчика) и **удаления
чего-либо** — ни одной стирающей функции, по той же причине, по которой
в банковских модулях нет платёжных поручений; за этим следит
`YandexDiskClientTests`.

Страница единицы оборудования — с v2.76.0
(`views.repair_order_unit_detail`, `/repair-orders/<заказ>/equipment/<строка>/`).
Всё про один прибор в одной работе: приём, диагностика, ремонт, детали
этой единицы, документы, папка на Диске, техкарты и материалы модели,
гарантия и история.

С v2.78.0 страница **правится**, а с v2.95.0 — **по разделам**:
`repair_order_unit_edit` (только POST) получает имя раздела полем
`section` и берёт форму из `views.UNIT_SECTION_FORMS`
(`diagnosis` → `UnitDiagnosisForm`, `repair` → `UnitRepairForm`).
Список **явный**: незнакомое имя не сохраняет ничего — подсунуть
в запрос можно что угодно. Возврат — к тому же разделу (`#<section>`).

Разделов два, а не одна форма на страницу, **намеренно**: сохранение
раздела пишет только его поля. Одна общая форма означала бы, что
открывший страницу утром и сохранивший вечером затирает всё, что за день
вписал сосед, — а прибор в работе бывает у двоих.

**Отдельной страницы дефектации нет с v2.95.0.** Приём, дефектация
и диагностика — один раздел `diagnosis` на этой же странице: что
привезли и что нашли внутри записывают за один заход, с прибором
на столе. Туда же переехали прайс с кнопкой «Подставить», техкарты
и материалы модели. `stamp_defect_act_date()` и `freeze_list_price()`
зовутся при сохранении **этого** раздела — раньше их звала страница
дефектации. Адрес `repair_order_defect_act_edit` оставлен
**переадресацией** на `#diagnosis`, а не убран: на него ведут закладки
мастеров и ссылки из переписки, и 404 выглядел бы как пропавшая
дефектация. Второго места правки это не создаёт — своей формы там нет.

Готовность на этой странице — **цвет самих разделов**, а не список внизу
(`readiness_sections`, правила `.unit-section-*` в самом шаблоне).
Список стоял в стороне от полей, которые его закрывают. Какой пункт
к какому разделу относится, записано четвёртым полем в `READINESS_CHECKS`
— разъедься эти два места, раздел горел бы недоделанным при заполненном
поле. Цвет задан **своими** правилами: Bootstrap приходит из интернета,
а без цвета страница перестала бы отвечать на главный вопрос, с которым
на неё приходят. Чек-лист на карточке заказа остаётся — он отвечает
на другой вопрос: что осталось по всем приборам заказа сразу.

Кнопка «Применить рецепт деталей» на этой же странице зовёт **тот же**
`repair_order_apply_fault_template`, что и форма заказа, — второй такой
обработчик разошёлся бы с первым, а списание со склада не то место, где
это допустимо. Работает от **сохранённых** неисправностей, не от
намеченных в форме, и уходит через `LiftTeamWS.fetch`; вложенной формой
её сделать нельзя — вложенных форм в разметке не бывает.

**Страница, а не окно**: окна рисует Bootstrap, а он приходит
из интернета; сюда же ведёт наклейка с прибора, и ссылку надо давать
в переписке. В список деталей попадают только списанные **на эту
единицу** — списанное «на заказ целиком» приписывать наугад нельзя.

В строке карточки заказа пять кнопок: записать работы (ведёт на страницу
единицы к `#repair`), списать деталь (не уводит — подставляет единицу
в форму списания ниже и доводит до неё), акт дефектации, этикетка, папка
на Диске. Кнопки «страница единицы» там нет намеренно: на страницу ведёт
вся строка и серийный номер в ней, а место отдано тому, что жмут
по многу раз в день.

Серийный номер — настоящая ссылка, и вся строка
кликабельна (`.unit-row[data-href]`). Обработчик пропускает щелчки
по `a, button, input, label, select, textarea` и по выделению текста:
галочка отмечает единицу для печати этикеток пачкой, кнопки ведут каждая
в своё место, а серийники из строки копируют. Столбец гарантии оттуда
убран (почти всегда пустой), но повторное обращение по чужой гарантии
помечено значком — это повод не брать денег. Длинные тексты в строке
обрезаны: раньше в ячейку шёл весь абзац.

Готовность единицы — с v2.71.0, и **отдельного поля состояния
у `RepairOrderEquipment` нет намеренно**: любое такое поле проставляют
руками и забывают, и оно начинает врать. Всё выводится из уже
заполненного — `readiness()`, `readiness_pending`, `is_ready`,
`readiness_label`, а по заказу `RepairOrder.readiness()`.

Список проверок один на всю программу — `READINESS_CHECKS`: отметка
в строке таблицы единиц, чек-лист на карточке заказа, страница массовой
отгрузки и предупреждение при смене статуса читают его, а не перечисляют
условия каждая по-своему. Порядок в нём **значимый** — по ходу работы:
дефектация, выполненные работы, списание запланированных деталей,
стоимость. Список читают сверху вниз, и он обязан читаться как сама
работа.

Стоимость проверяется **фактическая** (`repair_cost`), а не оценка
из дефектации: по ней считается сумма заказа и выставляется счёт. До
v2.80.0 проверялась `estimated_cost`, и единица с проставленной
стоимостью числилась неготовой. На гарантийном ремонте
(`warranty_case == 'warranty'`) пункт стоимости **выпадает из списка
вовсе**, а не помечается выполненным: ложная тревога учит не читать
и все остальные.

У каждого пункта есть `url` — куда идти, чтобы его закрыть или перечитать
(`_readiness_url`, считается рядом со списком проверок). Якорь — это
идентификатор самого поля (`#id_work_performed`), а курсор в него ставит
общий скрипт в `base.html`. В чек-листах пункты нарисованы **кнопками,
и выполненные тоже**: перепроверить написанное надо уметь в один щелчок.
Ссылки, оформленные кнопками, а не `<button>` — чтобы открывались
в соседней вкладке и работали с клавиатуры.

Читают его четыре экрана: карточка заказа (чек-лист), список единиц
(отметка в строке), список заказов (столбец «Готовность», с v2.77.0)
и дашборд (блок «Готово к отгрузке», с v2.77.0 — заказы в работе,
у которых готовы все единицы). Отгруженные и неремонтопригодные
ни там, ни там не тревожат: доделывать по ним нечего.

Ничего не запрещается: `_warn_about_unfinished_units` только говорит,
и только на `READINESS_WARNING_STATUSES` («готов к отгрузке», «отгружен»,
«частично отремонтирован» — с v2.97.0). Мастер видит прибор, а программа
нет; запрет означал бы, что статус проставляют «как-нибудь», лишь бы
программа пропустила. Экраны, где
готовность считается по многим строкам, обязаны делать
`prefetch_related('faults', 'details')` — без него карточка заказа,
список заказов, дашборд и страница массовой отгрузки уходят в десятки
лишних запросов; за этим следит
`ReadinessEverywhereTests.test_readiness_does_not_fan_out_into_queries`
(он меряет прирост запросов, а не их общее число: на списке заказов есть
и свой, давний, запрос суммы на каждый заказ).

Статус заказа «Частично отремонтирован» (с v2.97.0) — для смешанного
исхода: часть единиц заказа отремонтирована, часть — нет. Терминальный,
как «Отгружен» и «Ремонт невозможен» — не входит в `OPEN_STATUSES`,
входит в `TERMINAL_STATUSES` (аналитика загрузки инженеров) и в список
статусов, исключаемых из «заказов в работе» на дашборде. Заказчику
о нём сообщается тем же письмом, что о прочих финалах
(`notifications.notify_order_status`). Цвет — свой, не бутстраповский
класс (`.status-partial` в `base.html`): контекстных цветов Bootstrap
на шесть статусов уже не хватает, а путать его с жёлтой «Диагностикой»
нельзя, это разные и по смыслу далёкие статусы.

Раскраска статуса заказа — одно место на всю программу,
`models.order_status_css` (список заказов, карточка заказа, история
статусов, дашборд читают его, а не повторяют цепочку `{% if %}` каждый
у себя) — тот же приём, что у `complexity_css`, и то самое расхождение,
о котором предупреждал её docstring («так уже вышло со статусами
заказа»), наконец устранено.

Технологические карты — с v2.69.0. `TechCard` привязана
к **модели всегда**, к неисправности — по желанию: «как разобрать корпус»
не про поломку, а про прибор (это решение владельца, до v2.69.0 в планах
стояло обратное). Обе привязки сразу противоречия не создают —
неисправность сама живёт у модели, и `clean` следит, чтобы модель была
та же. `SET_NULL` у неисправности: убрали её из справочника — процедура
никуда не делась, карта становится общей.

`TechCardStep` несёт **исполнение**, а не карта целиком: при трёх
исполнениях иначе вышло бы три почти одинаковых карты, и правку пришлось
бы вносить трижды. Отбор — `TechCard.steps_for(version)`, общие плюс
помеченные им, без вытеснения (то же правило, что у материалов).
Номер шага задаёт человек — их ставят с запасом (10, 20, 30), чтобы
вставить новый, не перебивая остальные.

Показываются на странице дефектации рядом с материалами, и **ссылка
несёт исполнение единицы** (`?version=`): без него мастер увидел бы
половину карты и не понял, что половины нет. Исполнение, которого
у модели нет, страница называет вслух, а не молча показывает общие шаги.
Печать — свой лист A4 в `tech_cards/detail.html`, правила печати свои,
не бутстраповские. Предостережение печатается со словом «Внимание»
и в рамке: на бумаге цвет уходит в серый.

Снимок к шагу (`TechCardStep.image`, с v2.70.0) — **единственный файл,
который программа хранит у себя**. Всё остальное по-прежнему ссылками
(`EquipmentMaterial`): схему на Диске правят, а снимок шага никто
не правит. Уменьшается до сохранения — `core/images.shrink_photo`,
вызывается из `TechCardStepForm.clean_image`, одним местом: длинная
сторона 1600, PNG остаётся PNG (скриншот схемы в JPEG размыл бы подписи
на выводах), остальное в JPEG, ориентация из EXIF применяется.
`image.format` читается **до** `exif_transpose` — после него он пустой.
Больше `MAX_UPLOAD_BYTES` (15 МБ) не принимается: это снимок с телефона,
а не схема.

Файл при удалении шага **не стирается** намеренно: он весит около сотни
килобайт, а стирание по случайно удалённой строке — способ потерять
снимок, который переснять уже негде. Замена снимка тоже оставляет старый
файл; обе крохи забирает ночная выгрузка и держит в облаке.

`media/` попадает в резервную копию с v2.70.0: `deploy/backup.sh` шлёт
её тем же `rclone copy` (не `sync`) в подкаталог `media` того места, куда
уходят копии базы. Отдельной настройки на работающей установке
не требуется — за этим следит `MediaInBackupTests`. nginx отдаёт
`/media/` и до этого.

Чего в картах нет: копирования шагов между исполнениями — наследования
между ними нет и заводить его нельзя.

Материалы модели — с v2.68.0. `EquipmentMaterial` — **ссылка, а не файл**:
схема, инструкция, методика проверки. Файлов программа не хранит и хранить
не будет — материалы правят на Диске, копия разошлась бы с оригиналом
молча, а схема в приличном разрешении весит десятки мегабайт при жизни
на карте памяти. Заводятся в карточке модели (`equipment_model_edit`,
набор форм `EquipmentMaterialFormSet`), показываются на странице
дефектации (`repair_orders/defect_act_form.html`). На странице **создания**
модели их нет намеренно: вешать ссылки не на что.

Отбор — `EquipmentModel.materials_for(version)`: общие **плюс**
помеченные этим исполнением. Вытеснения здесь нет, и это отличие
от рецепта деталей намеренное: там вытесняется строка **по той же
детали**, а тут вытеснять нечего — схема исполнения и общая инструкция
нужны обе. Порядок видов значимый (схема первой) и берётся из одного
списка `EQUIPMENT_MATERIAL_KINDS`; он на уровне модуля, потому что
`class Meta` имён своего класса не видит.

Сама типовая неисправность может быть отмечена под несколько исполнений
(`FaultType.versions`, M2M, с v2.97.0) — раньше отбора по исполнению
не было вовсе: неисправность либо принадлежала всей модели, либо
не существовала. Пусто — по-прежнему общая для всех исполнений модели
(архитектура не изменилась, «сохнут те же конденсаторы»); отмечены —
предлагается только для них, и `applicable_to(version)` решает это
одним местом. Форма диагностики на странице единицы фильтрует список
по исполнению прибора, но не теряет уже выбранную неисправность, даже
если ограничение завели после того, как её выбрали, — иначе раздел
отказался бы сохраняться из-за собственной же более поздней настройки.
Это отдельная привязка от `FaultTypePart.version` ниже: там уточняется
рецепт **внутри** уже применимой неисправности, здесь — применимость
самой неисправности.

Строка рецепта неисправности (`FaultTypePart`) может нести версию:
пусто — общая строка для всех исполнений, версия — уточнение, которое
вытесняет общую строку **по этой же детали и только у этого исполнения**.
Остальные детали берутся общими, наследования между версиями нет
и заводить его нельзя: применимость проставляется руками. Собирает
итоговый рецепт `FaultType.recipe_lines(version)`, версию единицы
в применение шаблона передаёт `equipment_id` в POST.

Копирование справочных карточек (с v2.54.0, типовая неисправность вместе
с рецептом и карточка детали) устроено одинаково и одним приёмом:
`?copy_from=<номер>` у страницы **создания** заполняет форму образцом,
и до нажатия «Сохранить» в базе не появляется ничего. Прайсов ещё нет —
когда появятся, копирование им делать тем же приёмом, а не новым.
У копии детали не подставляется артикул: он уникален, и два одинаковых
форма всё равно не примет.

Сканер штрихкодов — с v2.55.0. Устройство: разбор кода на сервере —
`core/scanning.py` (`decode` → `{kind, id}` или `None`), тот же разбор
в браузере — `core/static/js/scanner.js`, вид сообщений —
`core/static/css/scanner.css` (оба подключены в `base.html` на каждой
странице), страница «Сканирование» — `views.scan_page` (`/scan/`)
и `views.scan_resolve` (`/scan/resolve/`).

Сканер — **клавиатура**: он набирает содержимое кода и жмёт Enter.
Никакого доступа к устройству у страницы нет и не будет, отличить сканер
от человека можно только по скорости. Считается **средняя** скорость
(`MAX_AVERAGE_MS`, 30 мс на знак), а не каждый промежуток по отдельности:
проверка в браузере показала, как заминка посреди кода разрывает его
пополам и деталь превращается в «это не наш код». Восстановление поля
(`restoreSnapshot`) обязано идти **до** `forget()` — иначе снимок стирается
вместе с набором и обрывки кода остаются в поле.

Уровень восстановления QR — **H** (около 30 % повреждённой площади),
с v2.92.0, `utils.generate_qr_image`. Взят даром: содержимое короткое,
и код остался тем же 21 модулем. Это и есть вторая причина, по которой
адреса сервера в коде быть не должно, — при полной ссылке уровень H
дал бы 37 модулей вместо 29, и на 12,3 мм код перестал бы читаться.
За обоими условиями следит `QrErrorCorrectionTests`.

В код кладётся **короткое содержимое без адреса сервера** — `u/123`
(`views.qr_payload`). Сканируют, когда программа уже открыта, и адрес
в коде не нужен ни для чего, а занимал три четверти содержимого: 38 знаков
против пяти. На этикетке заказа это разница между 29 модулями (2,6 точки
принтера на модуль, впритык к пределу) и 21 (3,6 точки). Второе следствие
важнее: внутренний адрес больше не печатается на наклейках, уезжающих
к заказчику. Полная ссылка (`views.qr_link`) показывается **на экране**
страницы печати — чтобы ошибку в адресе было видно там, а не со сканером
у стеллажа.

Вид кода узнаётся **по виду пути, а не по адресу сервера**: наклейки,
напечатанные до v2.61.0, несут ссылку целиком и читаются по-прежнему —
переклеивать их по всему складу некому. Всё, что не одна из пяти форм
(`p`, `c`, `e`, `o`, `u`), — чужой код, о чём и говорится; догадок нет.

`u` — **единица оборудования в заказе**, и это то, что наклеено на самом
приборе (`views.short_order_equipment`). С v2.76.0 ведёт на **страницу
этой единицы** (`repair_order_unit_detail`). До v2.61.0 наклейка вела
на заказ целиком (в код помещался адрес сервера, и на позицию знаков
не оставалось), с v2.61.0 — в карточку заказа к нужной строке; и то,
и другое было не от хорошей жизни: страницы единицы просто не было.
Якорь `#unit-<id>` и подсветка правилом `:target` на карточке заказа
остаются — на них ведут чек-лист готовности и список деталей.

Подписка экрана: `LiftTeamScanner.register({kinds, name, onScan})`,
`handle.remove()`. Отвечает **последняя** подписка, и только она — скан
не разыскивается по нижним экранам. Не тот вид — сообщение и кнопка
обычного перехода, молчаливого бездействия быть не должно. Без подписки
скан открывает объект. Экрану, которому нужны два вида, перечислить оба
в одной подписке.

Камера — второй сканер, с v2.73.0: `core/static/js/camera-scan.js` читает
QR и отдаёт содержимое в `LiftTeamScanner.submit()`. **Экраны из-за неё
не менялись и меняться не должны** — иначе у одного и того же скана
появилось бы два разных поведения. Кнопка — вставка
`core/templates/core/_camera_button.html` (`data-camera-scan`), стоит
на «Сканировании», пересчёте инвентаризации и сетке кассетниц; новое
место — одна вставка.

Распознаёт **браузер** (`BarcodeDetector`), своей библиотеки нет и заводить
нельзя: стороннее приезжает из интернета, а его нет ровно тогда, когда
сканируют у стеллажа. Safari и всё на iOS не умеют — программа говорит
об этом вслух, как и про отсутствие HTTPS, запрет доступа и ненайденную
камеру. Молчаливого «не получилось» быть не должно.

Камеру страница получает **только в защищённом окружении**: HTTPS либо
localhost. Это свойство браузера, обходных путей нет и искать их не надо.
Сертификат даёт Tailscale (`deploy/nginx-lifteam-https.conf`,
`deploy/lifteam-cert.timer`, DEPLOY.md «HTTPS и камера»); со стороны
приложения ничего не потребовалось — `SECURE_PROXY_SSL_HEADER`,
`SECURE_SSL_REDIRECT` и `CSRF_TRUSTED_ORIGINS` в `settings_pi.py` были
заведены раньше. Своё окно камеры прячется атрибутом `hidden`, дорожки
отпускаются на закрытии и на `pagehide`, а повтор одного кода в кадре
гасится своим окном `SAME_CODE_MS` — секунды из слоя сканера мало,
камера видит наклейку непрерывно.

Оборудование, лежащее в другом незакрытом заказе, к приёму
**не предлагается** — один прибор не может стоять на двух верстаках.
Отбор один на всю программу: `available_equipment_for_order(exclude_order)`
(форма приёма заказа, форма приёма единицы на карточке, проверка в
`repair_order_add_unit`). Отгруженное и завершённое в списке остаётся:
прибор у заказчика и приедет снова — ради этого история ремонтов
и ведётся по единице, а вернувшийся выбирают из справочника, а не
заводят заново.

`exclude_order` нужен там, где выбирают среди единиц уже существующего
заказа: без него его собственные единицы считаются занятыми в нём же.
Карточка заказа передаёт его в `available_equipment` для формы приёма
единицы; на приёме заказа его нет и быть не может — заказа ещё нет.

Приём по одной единице — с v2.63.0: форма «принять ещё единицу» прямо
на карточке заказа (`views.repair_order_add_unit`, только POST). Сохранение
уводит **на страницу наклейки**, оттуда «Печать» и «Назад» возвращают
к следующей коробке. Переход, а не открытие окна из скрипта: окно,
открытое не по щелчку человека, браузер часто не показывает вовсе, и
наклейка молча не печаталась бы. Нового оборудования в этой форме нет —
его заводят при редактировании заказа, где для этого есть вся оснастка;
приезжавшее раньше проще отсканировать.

Первый рабочий экран, подписанный на скан, — **форма заказа**
(`repair_orders/form.html`, `registerIntakeScanner`). Принимает два вида,
`equipment` и `order_equipment`: наклейка бывает и на самом приборе,
и от прошлого заказа, а ведут они к одной и той же железке — поэтому
в описании скана есть отдельное поле `equipment_id` (у кода `u` номер
в коде — это строка заказа, а не единица, и одного `id` мало).

Отсканированная единица встаёт **в первую свободную строку**, а если
свободных нет — в новую: поднёс коробку, поднёс следующую, и каждая
встаёт на место без единого щелчка. Выбор применяется **событием**
`change`, а не присваиванием значения: на событии висят подсказка
о прошлых ремонтах, список типовых неисправностей и пересчёт занятых
вариантов. Повторный скан той же единицы — отказ вслух с указанием
позиции: молчание человек примет за несработавший сканер.

Карточка заказа подписана на те же два вида: скан ставит единицу в форму
приёма и переводит курсор в поле неисправности.

Складские экраны подписаны с v2.67.0, и подписка у каждого своя.
Пересчёт инвентаризации (`inventory/count.html`) принимает `part` и `cell`:
деталь — её строка, ячейка — первая строка этой ячейки; строки несут
`data-part`/`data-cell`, потому что искать строку по напечатанному тексту
нельзя — артикул может оказаться куском названия соседней детали.
Сетка кассетниц (`storage_cells/grid.html`) принимает те же два вида:
ячейка своей кассетницы раскрывается на месте, чужая открывается коротким
адресом `/c/<id>/`, деталь подсвечивает свою ячейку по полям `cell_id`
и `cabinet_number` из `scan_resolve` (адрес «К1-Р1-Я3» для этого не годится:
его пришлось бы разбирать обратно). В режиме перемещения ячейка — это
назначение, и `performMoveToCell` возвращает исход наружу: сказать
«переложено», когда перекладка не удалась, хуже, чем не сказать ничего.
Карточка детали (`parts/detail.html`) принимает `cell` и **только выбирает**
её в поле «назначить» — назначение снимает деталь с прежней ячейки,
и делать это по одному поднесению кода нельзя.

Список радиодеталей намеренно не подписан: без подписки скан открывает
карточку детали, а это ровно то, что там и нужно.

Перемещение — с v2.104.0 либо одной детали, либо **ячейки целиком**
(`moveWholeCell`, кнопка «Переместить ячейку целиком» в окне ячейки,
видна только когда в ней что-то лежит). Второго обработчика на сервере
это не потребовало по духу, но и не обошлось одним: `storage_cell_move`
по-прежнему берёт одну деталь по `part_id`, а `storage_cell_move_all` —
всё, что лежит в ячейке-источнике, тем же приёмом (адресат может быть
не пустым, тогда содержимое объединяется). `performMoveToCell` на
экране сам выбирает, какой из двух звать, по `moveWholeCell`.

Окно ячейки и подсказка при наведении на неё (с v2.106.0) показывают
не только артикул, но и тип компонента с корпусом — различить похожие
артикулы можно, не открывая карточку детали.

Фильтр «Без ячейки» (с v2.106.0) — на **вкладке радиодеталей**
(`part_list`, чекбокс в свёрнутых условиях), а не на сетке кассетниц:
это фильтр по **деталям**, у которых пуста `storage_cells` (M2M), а не
по физическим ячейкам сетки — с сеткой такое поле не смешать, у неё
и так виден каждый пустой ящик цветом. Отбор — `no_cell` в `_filter_parts`,
том же общем месте, что у остальных условий списка; `isnull=True` по M2M
не двоит строки, `distinct()` не нужен.

Тот же признак «без ячейки» решает, что показывает поиск детали
в окне ячейки на сетке кассетниц (`addPartPicker`, кнопка «Добавить
деталь в эту ячейку…»): пока поле поиска пустое, `_part_picker.html`
с параметром `default_no_cell=True` шлёт в `part_search` тот же `no_cell=1`
(`part-picker.js`, `data-default-no-cell`) — предлагаются детали, которым
ещё некуда лечь, а не весь каталог. Стоит начать печатать — ограничение
снимается: ищут именно то, что набрали, а «без ячейки» тут больше ни
при чём. Открытие ячейки на сетке (клик по плитке, скан, переход по
QR) **сразу открывает** эту панель и ставит курсор в строку поиска —
слушатель на `shown.bs.modal` кликает по `.part-picker-open` за
человека: открыли ячейку почти всегда затем, чтобы в неё что-то
положить, а не только посмотреть, что уже лежит.

Между разными кассетницами перемещение — это переход на страницу нужной
с `move_from`/`move_part` (или `move_all=1`) в адресной строке: сетка
кассетницы одна на экране, чужую ячейку не подсветить. Из-за этого
`location.reload()` после успешного переноса **обязан** сперва вычистить
эти параметры (`cancelMoveMode`, `history.replaceState` до самого
reload) — до v2.104.0 не чистил, и перезагруженная страница снова
читала `move_from` из адреса и сама включала режим перемещения:
пунктирные рамки не снимались, а той же деталью можно было промахнуться
ещё в одну ячейку. Внутри одной кассетницы адрес чистым и был — там
перехода нет, `move_from` в строку никогда не попадал, поэтому баг
был виден только при переносе между разными кассетницами.

Окна сетки кассетниц рисует Bootstrap, и с v2.67.0 его отсутствие
страницу не роняет: `new bootstrap.Modal` обёрнут в `try`, все `show()`
и `hide()` — под проверкой. Пока обёртки не было, обработчик готовности
падал на первой строке, и вместе с окнами умирали режим перемещения,
переход с наклейки ячейки и подписка на сканер, стоящие ниже в той же
функции. Поэтому содержимое ячейки сканер **называет словами**, а не
только показывает в окне.

Чего в сканировании нет: журнала сканов (список на странице «Сканирование»
живёт в браузере и уходит с ней), множественного набора «просканируйте
пачку» и настройки сканера из программы (он клавиатура, настраивают его
его же служебными кодами).

Наборы полей у `views._part_label` и `_cell_label` обязаны совпадать
**целиком**, включая то, чего у детали не бывает (`items` — перечень
ячейки). Страницы пачек передают поля в шаблон поимённо, а у словаря
Python есть свои методы: не окажись ключа `items`, шаблонизатор находит
метод `dict.items`, вызывает его и печатает на наклейке весь словарь —
вместе с `<SparePart: …>` и содержимым кода. Ровно это и печаталось
до v2.93.0. Следит `BatchLabelContextTests`: каждое имя, которое просит
шаблон пачки, должно быть ключом словаря.

Складская этикетка (деталь и ячейка, шаблон один) читается **снизу
вверх** — с v2.91.0: у нижнего края артикул с характеристиками, над ним
описание или номиналы, наверху служебная строка (корпус, применимость,
адрес). Причина не в красоте: на передней стенке кассетницы есть выступ,
за который ящик выдвигают, и он закрывает верхнюю полосу. Наверх вынесено
то, чем не жалко пожертвовать, — адрес и так написан на самой кассетнице.

Описание и QR прижаты к **нижнему** краю (`justify-content: flex-end`
у текста, `align-items: flex-end` у полосы): пустое место всё равно
где-то будет, и лучше ему оказаться под выступом, чем между описанием
и артикулом. Длинное описание растёт вверх и обрезается **с конца**
(`label-fit.js`, `clampToFit` считает от высоты блока, а не от его
нижней границы: при выравнивании по низу текст вылезает вверх, и старая
проверка не срабатывала ни на одной строке — пропадало начало фразы).

Сортировка по клику на шапку — с v2.106.0, тем же приёмом, что
у `.clickable-row` чуть выше: разметке нужен один атрибут,
`<th data-sort="имя">`, а ссылку строит и клик ловит общий
`sortable-table.js`, подключённый в `base.html` на каждой странице.
Сортирует **сервер** — `views.sorted_by_request(queryset, request, fields)`,
где `fields` — явный словарь {имя в адресе: выражение для `order_by`},
тот же приём, что у `envfile.EDITABLE` и `READINESS_CHECKS`: подставленное
в запрос имя мимо словаря не сортирует ничего вместо того, чтобы упасть
или сортировать по случайному полю модели. Без `?sort=` список остаётся
в порядке, который задал сам список (обычно по номеру или по дате),
трогать его до клика незачем. Первый клик по столбцу сортирует

сбрасывает на возрастание; смена сортировки возвращает на первую
страницу — там же список, отсортированный по-старому, почти наверняка
не та часть, что нужна.

Заведено пока у трёх главных списков (радиодетали, заказчики, заказы
на ремонт) — как образец, а не как предел: у остальных таблиц вставить
сортировку тем же приёмом, без правки скрипта. Сортируемый не каждый
столбец: то, что не поле базы, а python-свойство или агрегат по связанным
записям («Ячейка» у детали, «Стоимость» и «Готовность» у заказа),
`order_by` не достанет — заводить для этого аннотацию по каждому такому
столбцу не стали, это отдельная работа с своими рисками (`Sum` поверх
уже нескольких M2M-соединений в том же запросе грозит задвоить суммы
вместе с `distinct()`).

Прайсы — с v2.64.0. `PriceList` бывает базовым (заказчик не заполнен,
такой ровно один — за этим следит `save()`) и заказчика (`OneToOne`
к `Client`, то есть у заказчика прайс один). `PriceListLine` — тип
оборудования, сложность и цена; сложность пустая означает «любая».

Цену ищет одно место — `PriceList.line_for(client, type, complexity)`:
сначала прайс заказчика, потом базовый, а внутри прайса строка ровно
под эту сложность вытесняет строку без неё. Тот же приём, что у рецепта
деталей: уточнение бьёт общее, но только там, где заведено. Поэтому
прайс заказчика не обязан повторять базовый — в нём держат лишь то,
о чём договорились иначе. Возвращается **строка**, а не число: мастеру
надо видеть, из чьего прайса пришла цена.

**Цена привязана к типу оборудования, а не к модели**: «привод дверей»
чинится за одни деньги независимо от того, чей он. Тип стоит у модели
(`EquipmentModel.equipment_type`); у модели без типа цену подставить
не из чего, и программа так и говорит.

Цена **предлагается, а не подставляется**: на странице дефектации она
показана рядом с полем, с кнопкой «Подставить». Акт подписывает мастер,
и вписать за него программа не вправе. При сохранении дефектации цена
прайса **замораживается** в `RepairOrderEquipment.list_price`
(`freeze_list_price`) и больше не меняется: правка прайса задним числом
не должна менять то, о чём договорились. Согласованная цена остаётся
в `estimated_cost`; расхождение показывает `price_differs_from_list`.
Отдельной истории цен нет намеренно — она нужна ровно там, где уже
записана, то есть в самом заказе.

Копирование прайса — тем же `?copy_from=`, что у типовых неисправностей
и карточек деталей: образец заполняет форму, и до «Сохранить» в базе
не появляется ничего.

а по этой записи потом считают, во сколько обошёлся ремонт. Варианта
«на заказ целиком» в выборе больше нет; подставленный в запрос чужой

Список деталей единицы **набирается, а списывается кнопкой**
(с v2.96.0): добавление на странице прибора всегда только намечает
(`is_planned`), а со стеллажа весь список уходит одной кнопкой —
`repair_order_unit_write_off_planned`, одной транзакцией. Так это
и происходит у стола: мастер вскрыл прибор, набрал, что менять, и только
потом идёт к полкам; до этого склад менялся, пока он ещё думал.
Наполовину списанный список хуже не списанного вовсе — по нему уже
не понять, что взято.

Списывает и пачка, и одиночная кнопка **одним кодом** —
`views._write_off_planned`: второй такой разошёлся бы с первым, а склад
не то место, где это можно позволить. Он же остаётся тем самым общим
путём (`_use_repair_order_part`): партии FIFO, затрата, запись в истории.

Скан детали или ячейки на странице единицы **кладёт деталь в поле
выбора и только** (`kinds: ['part', 'cell']`, `LiftTeamPartPicker.set`):
количество вводит человек, списание — кнопкой. Скан, сам меняющий
остатки, означал бы, что случайно поднесённая к сканеру наклейка
списывает деталь. Ячейка с одной деталью читается как эта деталь;
в ячейке несколько — программа называет их число и просит отсканировать
саму деталь, а не выбирает наугад. Номера деталей ячейки отдаёт
`views._scan_cell` полем `parts` — строкой для человека тут
не обойтись.

Рецепт типовой неисправности привязывает детали к той единице, из строки
которой нажали кнопку (`equipment_id` в POST — тот же, что уже выбирал
версию для уточнений рецепта). Выбор единицы при ручном списании
показывается **только когда приборов в заказе несколько**. `SET_NULL`,
а не `CASCADE`: единицу убрали из заказа — деталь со склада всё равно
списана, и терять запись о ней нельзя.

Возврат детали — с v2.66.0. Возвращается **в те партии, из которых
брали**, и разбираются они **в обратном порядке**: сначала та, из которой
брали последней. Это отменяет списание ровно наоборот тому, как оно
делалось, и сохраняет свойство FIFO — что старые партии израсходованы
раньше новых; разбор с начала перевернул бы очередь.

Возврат **не создаёт новой партии**: приход — это партия, из которой потом
списывают, а возвращённая деталь в новую партию не превращается. Склад
прирастает уменьшением `StockAllocation`, а движение типа `return`
заводится только затем, чтобы возврат был виден в журнале (`return` —
третий тип движения, партией он не является и в `allocate` не попадает).

Себестоимость возвращённого считается по тем же партиям и тому же правилу,
что и списание: партия без цены или часть, списанная вовсе без партии,
делают сумму неизвестной целиком. На неё заводится **отрицательная**
`OrderCost`, а не правится прошлая: по затратам считают прибыль, и след
стирать нельзя.

Возврат знает свои партии через `RepairOrderDetail.movement` — связь
списания с расходом. У списаний до v2.66.0 её нет, и такие строки
не возвращаются: `returnable` возвращает False, а программа говорит,
что партии неизвестны. Догадка здесь хуже отказа — неверный возврат
разъедет себестоимость, и заметят это через полгода в отчёте о прибыли.

Отложенное списание — с v2.66.1. `RepairOrderDetail.is_planned`: деталь
нужна по ремонту, но со склада ещё не взята. Остаток она не трогает
и заказу ничего не стоит — `cost` у запланированной **None**, а не ноль:
ноль попал бы в сумму как настоящая цифра. Запланировать можно и больше,
чем лежит на полке, — ради этого случая оно и нужно.

Списание запланированной идёт **тем же путём**, что обычное: строка
удаляется и заводится через `_use_repair_order_part`, а не считает партии
и затраты своим кодом. Второй такой код однажды разошёлся бы с первым.
Возвращать запланированную нечего — её убирают из плана.

Себестоимость по партиям — с v2.46.0 есть. Партия — сама входящая запись
`StockMovement` (отдельной модели `Batch` нет); каждый расход распределяется
по партиям строго по датам поступления (FIFO), связь — `StockAllocation`,
себестоимость заказа — `OrderCost` (сейчас заполняется только категория
`parts`, `labor`/`overhead` зарезервированы на будущее). Списания, сделанные
до v2.46.0, партии не имеют и не могут — восстановить это задним числом
нельзя.

Банков с v2.50.0 два: Т-Банк и Точка. Всё, что выше банка, работает
через общий интерфейс `core/invoicing.py` (`InvoiceProvider`, реализации
`TBankProvider` и `TochkaProvider`) и не знает, с каким банком имеет дело;
разницу знают только `core/tbank.py` и `core/tochka.py`. Логику Т-Банка
при этом не переписывали — её просто завели под интерфейс, и состав
запроса к нему не менялся. Точка **на живом счёте не проверена**: сайт её
документации из среды разработки недоступен, схема собрана по двум
независимым SDK и сверена между ними; что именно осталось
неподтверждённым, перечислено в шапке `core/tochka.py`. Наборы настроек
у банков разные и намеренно не смешаны: `TBANK_*` и `TOCHKA_*`.
Ссылки на PDF Точка не отдаёт вовсе (файл забирается по токену), поэтому
у её счетов `invoice_pdf_url` пусто — это свойство банка.

`TOCHKA_CUSTOMER_CODE` и `TOCHKA_ACCOUNT_ID` не подобрать и не взять
из реквизитов — это внутренние идентификаторы Точки (код клиента
отдельный от ИНН, `accountId` — не то, что печатают в справке о счёте),
и узнать их неоткуда, кроме как запросом к самому банку. Команда
`tochka_check` (с v2.105.0 — обоих: `tochka.get_customers` и
`tochka.get_accounts`) показывает список клиентов, подсказывая, у кого
из них `customerType: "Business"`, и список счетов рядом. Неверный
customerCode — по словам самой документации Точки, самая частая причина
отказа «Forbidden by consent»; разбор обоих ответов терпимый, как и у
выписки Т-Банка (`tochka.customer_list`/`account_list`, форма обёртки
не подтверждена). Путь `GET /uapi/open-banking/v1.0/accounts` подтверждён
примером curl из документации Точки, страница «Авторизация по
JWT-токену».

Юрлицо больше не одно. `Organization` с v2.50.0 — справочник: бухгалтеров
двое и работают они от разных юрлиц. Ровно одна запись помечена основной
(`is_default`, за этим следит `save()`), и `get_solo()` возвращает именно
её — имя осталось прежним, потому что печатные формы звали единственную
запись так. Поле `Organization.provider` связывает юрлицо с банком
один-к-одному (ограничение уникальности при непустом значении).
От какого юрлица идут документы заказа, решает **одно** место —
`RepairOrder.legal_entity()`: юрлицо банка выставленного счёта, иначе
основное. Не разводить эту логику по печатным представлениям: заказчик
не должен получать по одной работе документы от двух разных фирм.
А вот нумерация счетов сквозная, одна на всю программу и при двух
юрлицах — так решил владелец, и делить её по юрлицам не надо.

Поля счёта в заказе называются `invoice_sent_at`, `invoice_pdf_url`,
`invoice_error`, `invoice_provider`, `invoice_external_id`, а с v2.52.0
ещё и `invoice_paid_at` — отметка «банк сообщил об оплате», которая
деньгами не является. До v2.50.0 первые три звались `tbank_invoice_*`;
приставка стала врать, когда банков стало два.

Инвентаризация — с v2.47.0 есть (`InventorySession`, `InventorySessionLine`).
Область — всегда одна кассетница, режима «весь склад разом» нет. На
кассетницу одновременно допускается только одна незавершённая сессия.
Расхождение применяется не отдельной сущностью корректировки, а обычным
`StockMovement`: недостача — расход, распределённый по партиям через тот же
`StockAllocation.allocate()` (FIFO, без ручного выбора партии), избыток —
приход без цены (`unit_price=None`), обязательно с комментарием о причине.
Применяется расхождение против остатка на момент подтверждения, а не против
того, что было при старте сессии — если между ними прошло другое движение,
это видно на экране подтверждения отдельной пометкой. Планового
напоминания провести инвентаризацию нет — только ручной запуск.
