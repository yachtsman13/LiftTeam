# LiftTeam

Django-приложение для учёта заказов на ремонт лифтового оборудования и склада
радиодеталей. Работает в офисе на Raspberry Pi 4; сотрудники подключаются
локально и через интернет по Tailscale — с компьютеров, планшетов и телефонов.

**Правила работы над проектом — в [PROMPT.md](PROMPT.md). Прочитай его перед
первой правкой. Что делать дальше и что уже решено — в [PLAN.md](PLAN.md).** Здесь только то, что нужно, чтобы запустить проект с нуля;
процесс, соглашения и подводные камни описаны там и намеренно не дублируются.

## Запуск с нуля

База данных в репозиторий не входит (в ней реальные данные заказчиков), так что
свежий клон её не содержит. Развернуть пустую:

```bash
pip install -r requirements.txt
```

```bash
python manage.py migrate
```

```bash
python manage.py init_cells
```

```bash
python manage.py create_admin --username admin --name Administrator --password admin123
```

Эти учётные данные — только для разработки. На рабочей установке администратор
заводится с настоящим паролем по `DEPLOY.md`, и `admin123` там быть не должно.

## Проверка изменений

```bash
python manage.py test
```

Сервер разработки поднимается конфигурацией `lifteam` из `.claude/launch.json`
(порт 8000) — запускай через неё, а не вручную. Вход — теми же учётными
данными, что созданы выше.

## Чего в проекте нет

Это регулярно предполагают по ошибке, а затем строят на пустом месте:

- модели документов (`Document`) и счёта как сущности. Акты приёма,
  выполненных работ и дефектации и коммерческое предложение — это печатные
  формы заказа (шаблоны в `core/templates/core/repair_orders/`), нигде
  не хранятся и своих номеров не имеют; PDF собирает браузер, серверного
  рендеринга нет.
  Счёт — не печатная форма: его создаёт банк по запросу программы,
  и номер к нему задаёт отправитель, а не банк;
- методов, двигающих деньги: `core/tbank.py` читает выписку и выставляет
  счета (`invoice/send`), `core/tochka.py` только выставляет счета, но
  платёжных поручений нет ни там, ни там и быть не должно.
  Счёт создаёт документ, списать по нему деньги банк не даст никому;
- разноса денег по уведомлению банка. Приём уведомлений с v2.52.0
  работает у Т-Банка (см. отдельный раздел ниже), но `Payment`
  из уведомления не создаётся и `payment_status` не меняется: суммы
  в уведомлении Т-Банка нет вовсе. Оплата по-прежнему разносится
  человеком по выписке;
- мессенджеров, кроме MAX и Telegram (`core/messengers.py`); в них уходит
  только дефицит деталей и сводка по задолженностям — заказчикам всегда
  почта;
- бухгалтерии как таковой: `Payment` — это только поступившая по заказу
  сумма с датой, без проводок, счетов учёта и НДС;
- размеров ячейки в миллиметрах: `Cabinet` (с v2.37.0) хранит только число
  ячеек в каждом ряду, а размер на экране считается от него — ряд из
  четырёх рисуется крупными ящиками, из шестнадцати мелкими секциями;
- ответственного инженера у заказа — есть только автор смены статуса;
- поставок и продажи оборудования: коммерческое предложение строится
  из заказа на ремонт, предложений на поставку программа не делает;
- офлайн-режима: с v2.49.0 есть понятная реакция на обрыв связи (полоса
  вверху страницы, удержание POST-форм с сохранением введённого), но нет
  ни кэша страниц и справочных данных для чтения без связи, ни очереди
  действий, отправляемой самой при восстановлении. Второе — намеренный
  отказ: повтор с неясным исходом первой попытки задваивает заказы
  и списания. Service worker в проекте отсутствует.

Приём уведомлений от банков — с v2.51.0, и с v2.52.0 у Т-Банка он
работает. Устройство: два адреса (`/webhooks/tbank/`, `/webhooks/tochka/`)
в отдельном наборе маршрутов `core/webhook_urls.py`, представление
`core/webhook_views.py`, проверяющие и разбор в `core/webhooks.py`,
запись доставки — `WebhookDelivery`.

**Подписи у Т-Банка нет вовсе** — это свойство его вебхуков, а не наш
пробел, и искать её в документации больше не надо. Подлинность держится
на двух условиях, и оба обязательны: адрес отправителя из шести
документированных (`WEBHOOKS_TBANK_IPS`) **и** совпадение заголовка
`Authorization` с `WEBHOOKS_TBANK_SECRET` — секрет придумывает владелец
и сообщает банку письмом. Пустой секрет означает отказ: один список
адресов слишком слаб, чтобы остаться единственной проверкой. Сравнение —
`hmac.compare_digest`. За обратным прокси настоящий адрес считает
`webhooks.client_address`: последнее звено `X-Forwarded-For`, и только
если `REMOTE_ADDR` входит в `WEBHOOKS_TRUSTED_PROXIES`. Те же шесть
адресов перечислены в `deploy/nginx-lifteam-hooks.conf`; расходиться
списки не должны, за этим следит `WebhookTBankAddressListTests`.

Принимается **одно** событие — «Обновление статуса счета на оплату»
(`{"invoiceId": ..., "status": "PAID"}`). Событие «Операция по счету»
не принимается намеренно: связать операцию выписки с заказом можно
только гаданием, а выписку разносит человек. Найденному заказу
проставляется `invoice_paid_at` и ставится оповещение бухгалтерии;
`Payment` не создаётся, `payment_status` не меняется — суммы
в уведомлении нет. Не найден счёт — доставка получает состояние
`unmatched`, и банку всё равно отвечается 200: он повторяет доставку
при любом не-2XX, а повторять тут нечего. Ключ повтора — `invoiceId`.

Чего в приёме нет: у Точки не написано ничего и писать не из чего —
её документация об уведомлениях недоступна, её проверяющий отказывает
всегда и называет недостающее. Не подтверждено и имя поля, из которого
берётся `invoice_external_id` в ответе Т-Банка на выставление счёта
(`tbank.invoice_external_id`): читаются несколько правдоподобных имён,
принимается только значение вида UUID. Без него уведомление заказ
не найдёт — это единственное звено цепочки, проверяемое только на живом
счёте.

Под префиксом `/webhooks/` не должно оказаться ничего постороннего:
на Raspberry Pi nginx открывает в интернет ровно этот префикс и отвечает
404 на остальное (DEPLOY.md, раздел «Приём уведомлений от банков
из интернета»), так что случайный сосед под этим префиксом стал бы
доступен миру. За этим следит `WebhookUrlIsolationTests`.

Приложение целиком от интернета закрывает не `server_name`, а
`allow`/`deny all` по адресу отправителя в `deploy/nginx-lifteam.conf`:
заголовок `Host` подставляет кто угодно, и nginx выбирает блок по одному
только ему. До v2.52.0 там стоял `server_name _;`, который перестал
совпадать с чем-либо, как только блок уведомлений стал `default_server`, —
и приложение переставало открываться через nginx вовсе.

Состояние связи считает `core/static/js/ws-connection.js` — он же держит
сокеты; полоса и удержание форм — `core/static/js/connection-status.js`.
Отдельного опроса сервера «жив ли он» нет и заводить не надо: присутствие
держит сокет на каждой странице. Ответ сервера с ошибкой (4xx/5xx) обрывом
связи не считается. Полоса прячется атрибутом `hidden` и правилом в стилях
`base.html`, а не классом `d-none`: Bootstrap грузится из интернета и при
неполадках со связью может не приехать — то есть ровно тогда, когда полоса
и нужна.

WebSocket с v2.20.0 работает целиком: браузер подключается к `ws/stock/`
на страницах с остатками (`core/static/js/stock-updates.js`) и обновляет
цифры на месте. Раньше клиентской части не было вовсе. С v2.48.0 каналов
два: к остаткам добавилось присутствие сотрудников (`ws/presence/`), и оно
подключается на **каждой** странице. Логика переподключения после обрыва
общая — `core/static/js/ws-connection.js`; дублировать её в новых скриптах
не надо.

Присутствие — с v2.48.0. Отдельной модели нет: это поле `Employee.last_seen`
плюс настройка `PRESENCE_TIMEOUT_SECONDS` (90 с), а «в сети» — свойство
`Employee.is_online`, то есть чистая функция от них двоих. Флага «онлайн»
нет намеренно: его пришлось бы гасить при разрыве, а разрыв неотличим
от заминки в сети. По той же причине `disconnect()` отметку **не** трогает,
и закрывший браузер числится в сети до конца таймаута — это не баг.
Чего в присутствии нет: привязки к терминалу (идентичности рабочих мест
в проекте не существует вообще — ждёт авторизации по NFC), серверных
таймеров и опроса по расписанию (список рассылается на подключение,
на сигнал от браузера и на отключение — этого достаточно, потому что
сигнал шлёт каждый подключённый), а также истории присутствия: хранится
только последняя отметка, журнала «кто когда был» нет.

Выбор детали — с v2.53.0 один на всю программу и **обязателен везде**,
где указывают одну деталь: обычный `<select>` по каталогу больше не
рисуется нигде и заводить его заново не надо (за этим следит
`PartPickerEverywhereTests`). Устройство: вставка шаблона
`core/templates/core/_part_picker.html`, поведение —
`core/static/js/part-picker.js`, вид — `core/static/css/part-picker.css`
(оба подключены в `base.html` на каждой странице), поиск на сервере —
`views.part_search` (`/parts/search/`). Новое место выбора — одна вставка,
без правки скриптов.

Наружу выбор отдаёт **скрытое поле с номером детали под прежним именем**,
поэтому принимающие представления и формы при переходе не менялись и
менять их не нужно. Отбор — тот же `views._filter_parts`, что у списка
радиодеталей, выгрузки и печати пачки этикеток (он принимает словарь
параметров, а не запрос); второго набора условий заводить нельзя — «найдено
3» на складе и то, что предлагает выбор детали, обязаны совпадать.
В строке результата, кроме артикула и названия, обязательны остаток
и адрес ячейки: по ним решают, идти к полке или заказывать. Отдаётся
не больше `views.PART_SEARCH_LIMIT` (50) строк, и ответ прямо говорит,
что показано не всё (`limited`, `total`).

Два условия, оба нарушать нельзя: **никакого Bootstrap JS** (ни
`data-bs-*`, ни `modal` — Bootstrap приходит из интернета; панель прячется
атрибутом `hidden`) и запросы **только через `LiftTeamWS.fetch`**, иначе
обрыв связи выглядит как «ничего не найдено» вместо общей полосы вверху
страницы. Обработчики повешены на документ, а не на каждую разметку:
строки рецепта неисправности размножаются копированием готовой строки,
и выбор в копии обязан работать сам (копия при этом чистится вызовом
`LiftTeamPartPicker.reset`).

Чего в выборе нет: множественного выбора (везде выбирается ровно одна
деталь), заведения новой детали прямо из него и подсказок «недавно
выбранные» — истории выбора программа не хранит.

Короткое название типовой неисправности (`FaultType.name`) в документы
не попадает **никогда** — это правило, а не умолчание. В акт дефектации
и в коммерческое предложение идёт только `FaultType.description`, полная
формулировка; неисправность с пустым описанием не даёт в документ ничего,
и подставлять вместо описания название нельзя. Текст для документа
собирает одно место — `RepairOrderEquipment.document_fault_text` (и его
обёртки `diagnosis_document_text` для акта и `quote_line` для
предложения): сначала описания выбранных неисправностей, потом свободный
текст мастера. Разводить эту сборку по печатным шаблонам не надо —
заказчик не должен получить в одном документе описание, а в другом
цеховой жаргон. Заказ без выбранных типовых неисправностей печатается
ровно как до v2.54.0, и за этим следит `FaultTextInDocumentsTests`.

Сложность ремонта с v2.54.0 живёт у неисправности (`FaultType.complexity`,
простой/сложный): она свойство вида поломки, а не прибора. У единицы
в заказе остаётся прежнее правимое поле `repair_complexity` (простой/
средний/сложный) — пустое означает не «простой», а «не задавали», и тогда
сложность выводится из выбранных неисправностей: сложна хотя бы одна —
сложен весь ремонт (`derived_complexity`, `effective_complexity`,
`complexity_is_derived`). В предложение печатается `effective_complexity`.

Типы оборудования и версии моделей — с v2.54.0. `EquipmentType` —
справочник («Привод дверей», «Преобразователь частоты»), ссылка на него
стоит у **модели**, а не у единицы: любой EkoDrive 2.0 — преобразователь
частоты. Тип **не заменяет** `EquipmentModel.kind` и с ним не сливается:
`kind` — это приставка к названию модели в акте дефектации, которую
оставляют пустой, если родовое слово уже стоит в названии («Преобразователь
частоты Emotron»); подстановка типа в акт напечатала бы его дважды. Тип
в документы не идёт вовсе, он нужен прайсу заказчика (следующий этап).

`EquipmentVersion` — исполнение модели (EkoDrive 2.0-1.1 и 2.0-0.7)
с комментарием («алюминиевый корпус»). У единицы версия и дата
изготовления необязательны, у модели тип необязателен — пусто у всего,
что заведено раньше, и миграция ничего не выдумывает.

**Обозначение версии печатается везде** — в акте приёма, акте дефектации,
акте выполненных работ, на этикетке и в списках выбора. До v2.58.0 было
ровно наоборот («ни в один документ не идут»); владелец решение изменил:
одна и та же модель в разных исполнениях — разное изделие, и в документе
это должно быть видно.

Форма — **слитная приписка**, одной строкой и одним шрифтом:
`БУАД-7-31.4`, `EcoDrive-2.3-1.1`. **Разделитель хранится внутри
обозначения версии** (`.4`, `-1.1`), склейка — простое сложение строк.
Отдельного поля «разделитель» нет намеренно: на изделиях разделители
произвольные, правилом их не вывести, и такое поле заполняли бы руками
при каждой версии — тот же труд, только в двух местах.

Собирают обозначение два места, и разводить их по шаблонам не надо:
`Equipment.designation` (`БУАД-7-31.4`) — акт приёма, акт выполненных
работ, этикетка, `__str__` в списках; `Equipment.full_designation`
(`Привод дверей БУАД-7-31.4`) — только акт дефектации, там изделие
называют полностью. Родового слова на этикетке нет намеренно: оно съело
бы место на 43 мм.

**Комментарий к версии (`note`) не печатается нигде** — это по-прежнему
так: «алюминиевый корпус» нужен мастеру у стола, а не заказчику.
Версии нет — не печатается ничего, «исп. 1.0» вместо пустого поля
не выдумывается. За тем и другим следит `EquipmentVersionInDocumentsTests`.

В коммерческом предложении версии нет, потому что там нет и названия
модели: единица опознаётся серийным номером, а колонка «наименование» —
это текст неисправности.

Строка рецепта неисправности (`FaultTypePart`) может нести версию:
пусто — общая строка для всех исполнений, версия — уточнение, которое
вытесняет общую строку **по этой же детали и только у этого исполнения**.
Остальные детали берутся общими, наследования между версиями нет
и заводить его нельзя: применимость проставляется руками. Собирает
итоговый рецепт `FaultType.recipe_lines(version)`, версию единицы
в применение шаблона передаёт `equipment_id` в POST.

Копирование справочных карточек (с v2.54.0, типовая неисправность вместе
с рецептом и карточка детали) устроено одинаково и одним приёмом:
`?copy_from=<номер>` у страницы **создания** заполняет форму образцом,
и до нажатия «Сохранить» в базе не появляется ничего. Прайсов ещё нет —
когда появятся, копирование им делать тем же приёмом, а не новым.
У копии детали не подставляется артикул: он уникален, и два одинаковых
форма всё равно не примет.

Сканер штрихкодов — с v2.55.0. Устройство: разбор кода на сервере —
`core/scanning.py` (`decode` → `{kind, id}` или `None`), тот же разбор
в браузере — `core/static/js/scanner.js`, вид сообщений —
`core/static/css/scanner.css` (оба подключены в `base.html` на каждой
странице), страница «Сканирование» — `views.scan_page` (`/scan/`)
и `views.scan_resolve` (`/scan/resolve/`).

Сканер — **клавиатура**: он набирает содержимое кода и жмёт Enter.
Никакого доступа к устройству у страницы нет и не будет, отличить сканер
от человека можно только по скорости. Считается **средняя** скорость
(`MAX_AVERAGE_MS`, 30 мс на знак), а не каждый промежуток по отдельности:
проверка в браузере показала, как заминка посреди кода разрывает его
пополам и деталь превращается в «это не наш код». Восстановление поля
(`restoreSnapshot`) обязано идти **до** `forget()` — иначе снимок стирается
вместе с набором и обрывки кода остаются в поле.

В код кладётся **короткое содержимое без адреса сервера** — `u/123`
(`views.qr_payload`). Сканируют, когда программа уже открыта, и адрес
в коде не нужен ни для чего, а занимал три четверти содержимого: 38 знаков
против пяти. На этикетке заказа это разница между 29 модулями (2,6 точки
принтера на модуль, впритык к пределу) и 21 (3,6 точки). Второе следствие
важнее: внутренний адрес больше не печатается на наклейках, уезжающих
к заказчику. Полная ссылка (`views.qr_link`) показывается **на экране**
страницы печати — чтобы ошибку в адресе было видно там, а не со сканером
у стеллажа.

Вид кода узнаётся **по виду пути, а не по адресу сервера**: наклейки,
напечатанные до v2.61.0, несут ссылку целиком и читаются по-прежнему —
переклеивать их по всему складу некому. Всё, что не одна из пяти форм
(`p`, `c`, `e`, `o`, `u`), — чужой код, о чём и говорится; догадок нет.

`u` — **единица оборудования в заказе**, и это то, что наклеено на самом
приборе (`views.short_order_equipment`). Ведёт в карточку заказа сразу
к нужной строке (якорь `#unit-<id>`, подсветка правилом `:target`, без
скрипта); история ремонтов этой единицы — отдельной кнопкой в той же
строке. До v2.61.0 наклейка вела на заказ целиком, а какая это единица,
подсказывал только номер позиции рядом: в код помещался адрес сервера,
и на позицию знаков не оставалось.

Подписка экрана: `LiftTeamScanner.register({kinds, name, onScan})`,
`handle.remove()`. Отвечает **последняя** подписка, и только она — скан
не разыскивается по нижним экранам. Не тот вид — сообщение и кнопка
обычного перехода, молчаливого бездействия быть не должно. Без подписки
скан открывает объект. Экрану, которому нужны два вида, перечислить оба
в одной подписке.

**Камеры в браузере нет и быть не может** до HTTPS: камеру страница
получает только в защищённом окружении, а программа открывается по http
на имени в Tailscale. Обходных путей не искать — их нет.

Приём по одной единице — с v2.63.0: форма «принять ещё единицу» прямо

уводит **на страницу наклейки**, оттуда «Печать» и «Назад» возвращают

открытое не по щелчку человека, браузер часто не показывает вовсе, и
наклейка молча не печаталась бы. Нового оборудования в этой форме нет —
его заводят при редактировании заказа, где для этого есть вся оснастка;
приезжавшее раньше проще отсканировать.

Первый рабочий экран, подписанный на скан, — **форма заказа**
(`repair_orders/form.html`, `registerIntakeScanner`). Принимает два вида,
`equipment` и `order_equipment`: наклейка бывает и на самом приборе,
и от прошлого заказа, а ведут они к одной и той же железке — поэтому
в описании скана есть отдельное поле `equipment_id` (у кода `u` номер
в коде — это строка заказа, а не единица, и одного `id` мало).

Отсканированная единица встаёт **в первую свободную строку**, а если
свободных нет — в новую: поднёс коробку, поднёс следующую, и каждая
встаёт на место без единого щелчка. Выбор применяется **событием**
`change`, а не присваиванием значения: на событии висят подсказка
о прошлых ремонтах, список типовых неисправностей и пересчёт занятых
вариантов. Повторный скан той же единицы — отказ вслух с указанием
позиции: молчание человек примет за несработавший сканер.

Карточка заказа подписана на те же два вида: скан ставит единицу в форму
приёма и переводит курсор в поле неисправности.

Чего в сканировании нет: журнала сканов (список на странице «Сканирование»
живёт в браузере и уходит с ней), подписок на складских экранах
(склад, инвентаризация — следующий этап), множественного набора
«просканируйте пачку» и настройки сканера из программы (он клавиатура,
настраивают его его же служебными кодами).

Списки на телефоне — с v2.56.0. Устройство: один файл

«LT», а не логотип (см. PROMPT.md, раздел «Логотип»). Буквы под картинкой —
последний запасной вид на случай, когда не показалась и она: без него меню

загрузки случается раньше, чем доходит очередь до скриптов внизу страницы.

были недоступны вовсе. Пока меню открыто, страница под ним стоит

а докрученный до конца список не передаёт движение наружу
(`overscroll-behavior: contain`) — все три нужны, каждое закрывает свой
случай. Раскладка в столбец написана **своими** правилами,
хотя в разметке стоят и классы Bootstrap: без него пропала бы прокрутка
(`MobileSidebarScrollTests`).

Шаблон один на обе страницы. `_equipment_row.html` рисует поле, только

Прайсы — с v2.64.0. `PriceList` бывает базовым (заказчик не заполнен,
такой ровно один — за этим следит `save()`) и заказчика (`OneToOne`
к `Client`, то есть у заказчика прайс один). `PriceListLine` — тип
оборудования, сложность и цена; сложность пустая означает «любая».

Цену ищет одно место — `PriceList.line_for(client, type, complexity)`:
сначала прайс заказчика, потом базовый, а внутри прайса строка ровно
под эту сложность вытесняет строку без неё. Тот же приём, что у рецепта
деталей: уточнение бьёт общее, но только там, где заведено. Поэтому
прайс заказчика не обязан повторять базовый — в нём держат лишь то,
о чём договорились иначе. Возвращается **строка**, а не число: мастеру
надо видеть, из чьего прайса пришла цена.

**Цена привязана к типу оборудования, а не к модели**: «привод дверей»
чинится за одни деньги независимо от того, чей он. Тип стоит у модели
(`EquipmentModel.equipment_type`); у модели без типа цену подставить
не из чего, и программа так и говорит.

Цена **предлагается, а не подставляется**: на странице дефектации она
показана рядом с полем, с кнопкой «Подставить». Акт подписывает мастер,
и вписать за него программа не вправе. При сохранении дефектации цена
прайса **замораживается** в `RepairOrderEquipment.list_price`
(`freeze_list_price`) и больше не меняется: правка прайса задним числом
не должна менять то, о чём договорились. Согласованная цена остаётся
в `estimated_cost`; расхождение показывает `price_differs_from_list`.
Отдельной истории цен нет намеренно — она нужна ровно там, где уже
записана, то есть в самом заказе.

Копирование прайса — тем же `?copy_from=`, что у типовых неисправностей
и карточек деталей: образец заполняет форму, и до «Сохранить» в базе
не появляется ничего.

Детали на единицу — с v2.65.0, но только записью «куда ушла»:
`RepairOrderDetail.order_equipment` (пусто — «на заказ целиком»).
Склад, партии и себестоимость считаются ровно как считались — привязка
на них не влияет никак.

Правило заполнения выбрал владелец: **в заказе с одной единицей привязка
проставляется сама** (`RepairOrder.sole_equipment`), с несколькими —
остаётся пустой, пока мастер не укажет. Угадывать нельзя: в заказе
из пяти приборов программа не знает, в который поставили конденсатор,
а по этой записи потом считают, во сколько обошёлся ремонт. Списания
до v2.65.0 лежат пустыми, и заполнять их задним числом не надо.

Рецепт типовой неисправности привязывает детали к той единице, из строки
которой нажали кнопку (`equipment_id` в POST — тот же, что уже выбирал
версию для уточнений рецепта). Выбор единицы при ручном списании
показывается **только когда приборов в заказе несколько**. `SET_NULL`,
а не `CASCADE`: единицу убрали из заказа — деталь со склада всё равно
списана, и терять запись о ней нельзя.

Возврат детали — с v2.66.0. Возвращается **в те партии, из которых
брали**, и разбираются они **в обратном порядке**: сначала та, из которой
брали последней. Это отменяет списание ровно наоборот тому, как оно
делалось, и сохраняет свойство FIFO — что старые партии израсходованы
раньше новых; разбор с начала перевернул бы очередь.

Возврат **не создаёт новой партии**: приход — это партия, из которой потом
списывают, а возвращённая деталь в новую партию не превращается. Склад
прирастает уменьшением `StockAllocation`, а движение типа `return`
заводится только затем, чтобы возврат был виден в журнале (`return` —
третий тип движения, партией он не является и в `allocate` не попадает).

Себестоимость возвращённого считается по тем же партиям и тому же правилу,
что и списание: партия без цены или часть, списанная вовсе без партии,
делают сумму неизвестной целиком. На неё заводится **отрицательная**
`OrderCost`, а не правится прошлая: по затратам считают прибыль, и след
стирать нельзя.

Возврат знает свои партии через `RepairOrderDetail.movement` — связь
списания с расходом. У списаний до v2.66.0 её нет, и такие строки
не возвращаются: `returnable` возвращает False, а программа говорит,
что партии неизвестны. Догадка здесь хуже отказа — неверный возврат
разъедет себестоимость, и заметят это через полгода в отчёте о прибыли.

Отложенное списание — с v2.66.1. `RepairOrderDetail.is_planned`: деталь
нужна по ремонту, но со склада ещё не взята. Остаток она не трогает
и заказу ничего не стоит — `cost` у запланированной **None**, а не ноль:
ноль попал бы в сумму как настоящая цифра. Запланировать можно и больше,
чем лежит на полке, — ради этого случая оно и нужно.

Списание запланированной идёт **тем же путём**, что обычное: строка
удаляется и заводится через `_use_repair_order_part`, а не считает партии
и затраты своим кодом. Второй такой код однажды разошёлся бы с первым.
Возвращать запланированную нечего — её убирают из плана.

Себестоимость по партиям — с v2.46.0 есть. Партия — сама входящая запись
`StockMovement` (отдельной модели `Batch` нет); каждый расход распределяется
по партиям строго по датам поступления (FIFO), связь — `StockAllocation`,
себестоимость заказа — `OrderCost` (сейчас заполняется только категория
`parts`, `labor`/`overhead` зарезервированы на будущее). Списания, сделанные
до v2.46.0, партии не имеют и не могут — восстановить это задним числом
нельзя.

Банков с v2.50.0 два: Т-Банк и Точка. Всё, что выше банка, работает
через общий интерфейс `core/invoicing.py` (`InvoiceProvider`, реализации
`TBankProvider` и `TochkaProvider`) и не знает, с каким банком имеет дело;
разницу знают только `core/tbank.py` и `core/tochka.py`. Логику Т-Банка
при этом не переписывали — её просто завели под интерфейс, и состав
запроса к нему не менялся. Точка **на живом счёте не проверена**: сайт её
документации из среды разработки недоступен, схема собрана по двум
независимым SDK и сверена между ними; что именно осталось
неподтверждённым, перечислено в шапке `core/tochka.py`. Наборы настроек
у банков разные и намеренно не смешаны: `TBANK_*` и `TOCHKA_*`.
Ссылки на PDF Точка не отдаёт вовсе (файл забирается по токену), поэтому
у её счетов `invoice_pdf_url` пусто — это свойство банка.

Юрлицо больше не одно. `Organization` с v2.50.0 — справочник: бухгалтеров
двое и работают они от разных юрлиц. Ровно одна запись помечена основной
(`is_default`, за этим следит `save()`), и `get_solo()` возвращает именно
её — имя осталось прежним, потому что печатные формы звали единственную
запись так. Поле `Organization.provider` связывает юрлицо с банком
один-к-одному (ограничение уникальности при непустом значении).
От какого юрлица идут документы заказа, решает **одно** место —
`RepairOrder.legal_entity()`: юрлицо банка выставленного счёта, иначе
основное. Не разводить эту логику по печатным представлениям: заказчик
не должен получать по одной работе документы от двух разных фирм.
А вот нумерация счетов сквозная, одна на всю программу и при двух
юрлицах — так решил владелец, и делить её по юрлицам не надо.

Поля счёта в заказе называются `invoice_sent_at`, `invoice_pdf_url`,
`invoice_error`, `invoice_provider`, `invoice_external_id`, а с v2.52.0
ещё и `invoice_paid_at` — отметка «банк сообщил об оплате», которая
деньгами не является. До v2.50.0 первые три звались `tbank_invoice_*`;

Инвентаризация — с v2.47.0 есть (`InventorySession`, `InventorySessionLine`).
Область — всегда одна кассетница, режима «весь склад разом» нет. На
кассетницу одновременно допускается только одна незавершённая сессия.
Расхождение применяется не отдельной сущностью корректировки, а обычным
`StockMovement`: недостача — расход, распределённый по партиям через тот же
`StockAllocation.allocate()` (FIFO, без ручного выбора партии), избыток —
приход без цены (`unit_price=None`), обязательно с комментарием о причине.
Применяется расхождение против остатка на момент подтверждения, а не против
того, что было при старте сессии — если между ними прошло другое движение,
это видно на экране подтверждения отдельной пометкой. Планового
напоминания провести инвентаризацию нет — только ручной запуск.
