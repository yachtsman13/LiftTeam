# Техническое задание — LiftTeam v2.25.0

## 1. Общие положения

**LiftTeam** — система управления заказами на ремонт лифтового оборудования 
и складом радиодеталей (запчастей).

- Репозиторий: https://github.com/yachtsman13/Lifteam
- Автор: yachtsman13
- Лицензия: внутреннее использование

## 1.1. Источник кода и порядок сдачи работы

Источник истины — рабочая копия репозитория; изменения сдаются коммитом
в `main`, откуда их забирает Raspberry Pi кнопкой «Обновление».

Подробный порядок работы описан в [PROMPT.md](PROMPT.md) и здесь намеренно
не дублируется — при расхождении верен `PROMPT.md`.

До версии v2.7.x действовал другой порядок: код присылали файлом
`lifteam_code_vX.X.X.txt`, а результат возвращали архивом `Lifteam-vX.X.X.zip`,
и обращаться к GitHub было прямо запрещено. Этот порядок отменён вместе с
переходом на git. Требование сохранено здесь одной строкой потому, что на него
ссылались прошлые задания: если такая ссылка встретится, она устарела.

## 2. Функциональные требования

### 2.1. Аутентификация
- Авторизация по логину (username), не по email
- Кастомная модель Employee (расширение AbstractBaseUser)
- Роли: admin, warehouse, repair_manager, accountant
- Логин по умолчанию: admin / admin123

### 2.2. Заказчики (Client)
- CRUD операции
- Поля: название, ИНН, КПП, контактное лицо, телефон, email
- Поиск по названию и ИНН
- Выгрузка списка в Excel: реквизиты, число заказов, текущий долг

### 2.3. Модели оборудования (EquipmentModel)
- CRUD операции
- Поле: название модели (уникальное)

### 2.4. Оборудование (Equipment)
- CRUD операции
- Поля: модель, серийный номер (уникальный), текущий заказчик
- Печать этикетки 43x25 мм: QR со ссылкой `/e/<id>`, открывающей историю
  ремонтов этой единицы, плюс штрихкод Code 128 с серийным номером.
  Штрихкод не печатается, если в серийном номере есть кириллица — Code 128
  её не кодирует; в этом случае QR центрируется
- Поиск по серийному номеру, модели и текущему заказчику
- Отбор по гарантии: на гарантии / без гарантии
- Выгрузка отобранного списка в Excel с датой окончания гарантии и числом
  ремонтов каждой единицы
- Страница истории ремонтов единицы с выгрузкой в Excel: заказы, даты,
  заказчик, неисправность, пломбы, стоимость, гарантия и детали
- Гарантия на ремонт: срок задаётся параметром `WARRANTY_MONTHS` (по умолчанию
  12 месяцев) и отсчитывается от даты завершения заказа. Нигде не хранится,
  вычисляется от даты — изменение срока действует и на прошлые заказы
- Действующая гарантия видна в списке оборудования, в истории ремонтов,
  в заказе и — главное — подсказкой при выборе оборудования в новом заказе:
  повторное обращение в пределах гарантии видно до оформления

### 2.5. Заказы на ремонт (RepairOrder)
- Номер заказа генерируется автоматически: LT-YYYY-MM-XXXXX
- Поля: заказчик, оборудование (ManyToMany через RepairOrderEquipment), 
  дата приёма, описание неисправности, дата завершения, дата отгрузки,
  трек-номер, транспортная компания, номер счёта, дата счёта,
  статус оплаты, статус ремонта
- Статусы ремонта: принят, диагностика, ремонт, готов к отгрузке, отгружен
- Статусы оплаты: не оплачен, частично оплачен, оплачен
- История изменения статусов (OrderStatusHistory) с фиксацией пользователя
- Печать этикетки оборудования в заказе 43x25 мм: номер заказа с позицией,
  модель, серийник, дата приёма, логотип с QR внутри. QR содержит ссылку
  `/o/<id>`, открывающую заказ
- Inline-создание заказчика, модели оборудования и оборудования из формы заказа
- Добавление деталей в заказ со списанием со склада
- Предупреждение о несохранённых изменениях при уходе со страницы
- Расширенный поиск: одна строка ищет по номеру заказа, названию и ИНН
  заказчика, серийному номеру (в том числе в другом написании), модели
  оборудования, номеру счёта, трек-номеру и описанию неисправности —
  как заказа, так и отдельной единицы
- Дополнительные условия: статус ремонта, статус оплаты, заказчик, модель
  оборудования, диапазон дат приёма. Показывается число найденных заказов
  и кнопка сброса
- Выгрузка отобранных заказов в Excel кнопкой «В Excel»; последняя строка
  файла — итоговая сумма

### 2.6. Радиодетали / запчасти (SparePart)
- Поля: артикул (уникальный), название, тип компонента,
  сопротивление + ед.изм., мощность + ед.изм., напряжение + ед.изм.,
  ток + ед.изм., ёмкость + ед.изм., текущий остаток, минимальный остаток,
  срок поставки, предпочтительный поставщик, описание
- Импорт из Excel (.xlsx)
- Фильтрация по параметрам: диапазоны напряжения, тока, мощности,
  сопротивления и ёмкости. Нечисловое значение не применяется и не роняет
  страницу; запятая принимается как десятичный разделитель
- Фильтрация по остатку: диапазон и состояние (требуют внимания / только
  дефицит / только на минимуме)
- Три состояния остатка, одинаковые во всех разделах: **дефицит** (ниже
  минимума, попадает в план закупок), **на минимуме** (равен минимуму,
  только предупреждение) и норма. Условия заданы в `SparePartQuerySet`
  и свойстве `stock_state`
- Печать этикетки детали 43x25 мм — на пакет: артикул, название,
  характеристики, адрес ячейки и QR-код 15 мм со ссылкой `/p/<id>`
  на карточку детали
- Печать пачкой: отметки в списке либо весь текущий отбор, не более
  200 этикеток за раз. Раскладка «рулон» (по этикетке на страницу 43x25 мм)
  или «лист A4» (рядами, с пунктиром для резки)

### 2.7. Ячейки хранения (StorageCell)
- Кассетницы: 12 штук, 8 рядов, 8 ячеек в ряду
- Адрес: К{номер}-Р{ряд}-Я{ячейка}
- Визуальная сетка кассетниц (прямоугольные ячейки, без прокрутки).
  Цвет ячейки — худшее из состояний её деталей: серый свободна, зелёный
  норма, жёлтый на минимуме, красный дефицит
- Подписи рядов слева от сетки
- Перемещение деталей между ячейками (выбор кассетницы в модальном окне,
  выбор свободной ячейки — кликом по ячейке)
- Подсветка свободных ячеек в режиме перемещения
- Цвет ячейки обновляется живьём при изменении остатка её деталей; ячейка,
  выбранная для перемещения, не перекрашивается
- Печать этикетки 43x25 мм: адрес ячейки, содержимое и QR-код 15 мм
  со ссылкой `/c/<id>`, открывающей эту ячейку в сетке. Штрихкода на ней
  нет — адрес вида «К1-Р1-Я1» кириллический, а Code 128 кириллицу не кодирует
- Печать пачкой на всю кассетницу: только занятые ячейки или все подряд,
  раскладка «рулон» либо «лист A4»

### 2.8. Движение запчастей (StockMovement)
- Типы: приход, расход
- Поля: деталь, дата, количество, тип движения, номер документа,
  заказ на ремонт, примечания, кем создано (created_by)
- История движений с указанием пользователя
- WebSocket-уведомления об изменении остатков. Канал `ws/stock/` требует
  входа в программу. Браузер подключается к нему на страницах, где показан
  остаток (элементы с `data-stock-part`), обновляет цифры на месте
  и предупреждает о дефиците; при обрыве связи переподключается сам
  с нарастающей паузой до 30 секунд
- В сетке кассетниц по тем же сообщениям перекрашиваются ячейки

### 2.9. Отчёты
- План закупок (детали ниже минимального остатка)
- Журнал движений (с фильтрами по детали, типу, дате)
- Задолженности (неоплаченные заказы)
- Выгрузка каждого отчёта в Excel кнопкой «В Excel»; журнал движений
  выгружается с учётом выставленных на странице фильтров, в выгрузке
  задолженностей последняя строка — итоговая сумма
- Переход по страницам любого списка сохраняет поиск и фильтры

### 2.10. REST API
- ViewSets для всех сущностей
- Фильтрация, поиск, пагинация
- Эндпоинты для изменения статуса и статуса оплаты

### 2.11. Администрирование
- Управление пользователями (только для admin)
- Создание и редактирование пользователей

### 2.12. Оповещения (Notification)
- Очередь в базе: событие, получатель, тема, текст, состояние
  (в очереди / отправлено / не удалось / пропущено), число попыток,
  последняя ошибка, ссылка на заказ или деталь
- События: смена статуса заказа (заказчику — принят, готов к отгрузке,
  отгружен) и уход детали в дефицит (кладовщикам и администраторам)
- Постановка в очередь — в `core/notifications.py`, отправка — командой
  `send_notifications` по systemd-таймеру раз в 5 минут. Из обработчиков
  страниц письма не отправляются: SMTP не должен задерживать сохранение
- Параметры: `NOTIFICATIONS_ENABLED` (по умолчанию False), `NOTIFY_CLIENTS`
  (False), `NOTIFY_LOW_STOCK` (True), `NOTIFY_LOW_STOCK_COOLDOWN_HOURS` (24),
  `NOTIFICATIONS_MAX_ATTEMPTS` (5), `NOTIFICATIONS_MAX_AGE_HOURS` (24)
- Раздел «Оповещения» для администратора: очередь с отбором по состоянию
  и возвратом неудачных на повторную отправку

### 2.12.1. Каналы мессенджеров (MAX, Telegram)
- У оповещения есть канал: `email`, `max` или `telegram`. Получатель
  в мессенджере — не адрес почты, поэтому `recipient` не EmailField
- Транспорт — `core/messengers.py`, по одному POST на сообщение, только
  stdlib: ради одного запроса зависимость на Pi не добавляется
- В мессенджеры уходит только дефицит деталей и только сотрудникам.
  Заказчикам — по-прежнему почта: бота фирмы у них нет
- Каналы независимы: включать можно любой, оба или ни одного; неудача
  одного не мешает остальным. Очередь без писем не открывает SMTP
- Бот ни там, ни там не пишет первым: пока человек сам ему не написал,
  его идентификатор неизвестен. Идентификаторы вносятся вручную
  по выводу команд `max_updates` / `telegram_updates`
- При заданном `*_GROUP_CHAT_ID` сообщение уходит один раз в общий чат
  вместо личных

**MAX.** POST на `{MAX_API_URL}/messages?user_id=…`, токен в заголовке
`Authorization` без префикса. Получатель хранится как `user:<id>` или
`chat:<id>` — параметры запроса для человека и чата разные. Идентификатор
сотрудника — `Employee.max_user_id`. Параметры: `MAX_BOT_TOKEN` (пусто —
канал не настроен), `NOTIFY_MAX` (False), `MAX_GROUP_CHAT_ID` (пусто),
`MAX_API_URL` (`https://platform-api2.max.ru`; вынесен в настройки, потому
что адрес уже менялся).

**Telegram.** POST на `{TELEGRAM_API_URL}/bot<токен>/sendMessage` — токен
часть адреса, а не заголовок. Получатель хранится числом без приставок:
и человек, и группа — это `chat_id`, у группы он отрицательный.
Идентификатор сотрудника — `Employee.telegram_chat_id`. Отказ приходит
и с кодом 200 (`{"ok": false, "description": …}`), это проверяется
отдельно. Параметры: `TELEGRAM_BOT_TOKEN`, `NOTIFY_TELEGRAM` (False),
`TELEGRAM_GROUP_CHAT_ID`, `TELEGRAM_API_URL` (`https://api.telegram.org`;
меняется, если Telegram доступен только через зеркало).

### 2.13. Дашборд
- Плитки: всего заказов, активные, дефицит деталей (с числом деталей
  на минимуме), должники и сумма долга
- Разбивка заказов по статусам; каждый счётчик ведёт в список заказов
  с выставленным фильтром. Статусы без заказов показываются нулём
- Последние заказы и детали, требующие внимания: дефицит красным,
  «на минимуме» отдельной группой

## 3. Технические требования

### 3.1. Стек
- Python 3.12, Django 5.1, DRF 3.17
- Bootstrap 5, vanilla JS
- SQLite (standalone) / PostgreSQL 16 (Docker)
- Redis 7 (опционально), Django Channels, WebSocket
- Nginx (reverse proxy в Docker)

### 3.1.1. Поиск по русскому тексту

Встроенный в SQLite оператор LIKE приводит к одному регистру только латиницу,
поэтому поиск по кириллице зависел от регистра. Функция `like()` заменена
своей (`core/signals.py`), и `icontains` работает одинаково для русского
и латиницы во всех разделах. На PostgreSQL замена не применяется — там
регистронезависимый поиск работает сам.

### 3.1.2. Адрес в QR-кодах этикеток

Все четыре этикетки кодируют один и тот же адрес, `LABEL_BASE_URL`; на Pi
это по умолчанию адрес в Tailscale `http://100.108.92.92`. Смысл в том,
чтобы код не зависел от того, откуда открыли страницу печати: адрес
Tailscale одинаков в офисе, дома и в дороге, а локальный IP живёт только
внутри офисной сети. Плата — сканирующее устройство обязано быть в
Tailscale. Пустое значение возвращает прежнее поведение (адрес из запроса).

Хост из этого адреса автоматически добавляется в `ALLOWED_HOSTS`
и `CSRF_TRUSTED_ORIGINS` (`settings_pi.py`): без этого отсканированный код
приводил бы на «400 Bad Request».

Ссылки — без косой черты на конце (`/o/12`); соответствующие маршруты
заведены в `urls.py` рядом с каноническими. Экономия в один символ
удерживает этикетку заказа на 25 модулях: QR там 9,6 мм, при 29 модулях
выходит 2,5 точки принтера на модуль, что на практике не считывалось.
Порог — номер заказа до 1000.
