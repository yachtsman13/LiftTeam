# Развёртывание LiftTeam на Raspberry Pi 4

Инструкция для установки в офисе: Raspberry Pi 4 (4 ГБ), SQLite, доступ
локально и удалённо через интернет при сером IP.

Все команды выполняются на самом Pi — по SSH или с подключённой клавиатурой.

> **Выполняйте команды по одной, дожидаясь завершения каждой.** Если вставить
> в терминал несколько строк сразу, следующая команда попадёт в буфер, пока
> предыдущая ещё работает, и будет потеряна — а установка продолжится с
> пропущенным шагом, что выяснится позже и не очевидным образом.

> **Проверено на Windows, не на Pi.** Конфигурации написаны по документации,
> но на живом устройстве обкатываются впервые. Раздел «Если что-то не
> работает» — в конце.

---

## 1. Подготовка железа

### Загрузка с SSD вместо microSD

Самое важное решение во всей установке. microSD изнашивается от постоянной
записи и плохо переносит отключение питания — это основная причина потери
данных на Raspberry Pi. SSD на 120 ГБ через USB 3.0 стоит недорого и снимает
проблему.

1. Запишите Raspberry Pi OS Lite (64-bit) на SSD через Raspberry Pi Imager
2. В настройках Imager сразу задайте имя пользователя, пароль и включите SSH
3. Подключите SSD к синему порту USB 3.0, извлеките microSD
4. Pi 4 с актуальной прошивкой загрузится с USB автоматически

Берите Lite-версию без графической оболочки: она экономит память и ресурс
диска, а рабочий стол на сервере не нужен.

### Питание

Отключение электричества в момент записи в базу — реальный сценарий.
Минимум — источник бесперебойного питания на Pi и роутер. Даже недорогой
UPS, дающий пару минут, позволяет корректно завершить работу.

## 2. Подготовка системы

Обновите систему:

```bash
sudo apt update && sudo apt upgrade -y
```

Установите пакеты:

```bash
sudo apt install -y python3-venv python3-pip nginx git sqlite3
```

Создайте пользователя для приложения — работать от `root` или от вашей
учётной записи не нужно:

```bash
sudo useradd --system --home-dir /opt/lifteam --shell /bin/bash lifteam
```

```bash
sudo mkdir -p /opt/lifteam && sudo chown lifteam:lifteam /opt/lifteam
```

Каталог создаётся отдельно, без `--create-home`: иначе `useradd` положит
туда служебные файлы, и клонирование репозитория в непустой каталог
завершится ошибкой.

---

## 3. Установка приложения

```bash
sudo -u lifteam git clone https://github.com/yachtsman13/Lifteam.git /opt/lifteam
```

```bash
cd /opt/lifteam
```

```bash
sudo -u lifteam python3 -m venv venv
```

```bash
sudo -u lifteam venv/bin/pip install --upgrade pip
```

Установка зависимостей — самый долгий шаг, несколько минут:

```bash
sudo -u lifteam venv/bin/pip install -r requirements-pi.txt
```

Используйте `requirements-pi.txt`, а не `requirements.txt`: во втором есть
драйверы PostgreSQL и Redis, которые при SQLite не нужны, а на ARM ставятся
долго и иногда требуют компиляции.

## 4. Настройка

Сгенерируйте ключ приложения:

```bash
sudo -u lifteam venv/bin/python -c "from django.core.management.utils import get_random_secret_key; print(get_random_secret_key())"
```

Скопируйте полученную строку и создайте файл `.env`:

```bash
sudo -u lifteam nano /opt/lifteam/.env
```

Содержимое:

```ini
SECRET_KEY=сюда-вставить-сгенерированный-ключ
DEBUG=False
ALLOWED_HOSTS=192.168.1.50,lifteam.ваша-сеть.ts.net,localhost
TIME_ZONE=Europe/Moscow
```

В `ALLOWED_HOSTS` перечислите адреса, по которым будете открывать приложение:
локальный IP Pi в офисной сети и имя устройства в Tailscale (появится
на шаге 7). Если адрес не указан, Django ответит `400 Bad Request` — это
не ошибка, а защита от подмены заголовка `Host`. Имя из QR-кодов
(`lifteam.taile9b605.ts.net`) программа добавляет сюда сама — см. следующий
раздел.

### Адрес в QR-кодах этикеток

Все QR-коды на этикетках — деталей, ячеек и оборудования в заказе —
ведут на **имя Pi в Tailscale**: `http://lifteam.taile9b605.ts.net`.
Оно прошито в настройках, отдельно указывать ничего не нужно.

Именно имя, а не адрес `100.x`. Разница принципиальная: этикетка — бумажка,
адрес в ней впечатан навсегда. Адрес `100.x` закреплён за узлом, но меняется,
если узел удалить из тайнета и завести заново — например, при переустановке
системы на Pi. Все наклеенные к тому моменту этикетки после этого мертвы:
перепечатать их можно, отклеить с сотни пакетов — нет. Имя переживает
смену адреса.

Адрес Tailscale одинаков всюду: в офисе, дома и с телефона в дороге.
Этикетка читается независимо от того, кто и откуда её печатал. Локальный
IP так не умеет — напечатанная через Tailscale этикетка получала бы адрес,
недоступный из офиса, и наоборот.

**Плата за это: сканирующее устройство должно быть в Tailscale.** Телефон
без него получит «страница недоступна», даже стоя рядом с Pi. Убедитесь,
что Tailscale установлен на всех телефонах и планшетах, с которых
сканируют.

Отдельно разрешать этот адрес в `ALLOWED_HOSTS` не нужно: программа
добавляет его сама, иначе отсканированный код приводил бы
на «400 Bad Request».

**Значение из `.env` перебивает встроенное.** Если в `/opt/lifteam/.env`
уже есть строка `LABEL_BASE_URL` — например, с локальным IP из ранней
настройки, — коды пойдут на неё, а не на имя Tailscale, и обновление
программы этого не изменит. Проверить:

```bash
grep LABEL_BASE_URL /opt/lifteam/.env
```

Если строка есть и в ней локальный адрес, удалите её (тогда возьмётся
встроенное имя) или замените адрес на имя. После правки — перезапуск.
Что именно зашито в коды сейчас, написано под самим кодом на любой
странице печати.

Если имя другое или nginx вы не ставили и приложение отвечает на порту
8000, укажите адрес явно:

```ini
LABEL_BASE_URL=http://lifteam.taile9b605.ts.net:8000
```

Своё имя можно посмотреть на Pi:

```bash
tailscale status --json | grep -i dnsname
```

Пустое значение возвращает прежнее поведение — адрес берётся из того,
как открыта страница печати:

```ini
LABEL_BASE_URL=
```

Уже наклеенные этикетки не меняются: параметр действует на те, что
печатают после. Перепечатывать всё разом не нужно — старые ссылки
продолжают работать, пока работает адрес, который в них впечатан.

**Длина ссылки определяет размер QR-кода.** Границы (уровень коррекции M,
как в программе):

| Длина ссылки | Модулей в коде |
|---|---|
| до 26 символов | 25 |
| 27–42 | 29 |
| 43 и больше | 33 |

Самая тесная из трёх этикеток — оборудования в заказе: код там 9,6 мм.
При 29 модулях это 2,6 точки принтера на модуль, при 33 — уже 2,3, а 2,5
на практике не считывалось.

`http://lifteam.taile9b605.ts.net/o/1234` — 39 символов, то есть 29 модулей.
Ровно столько же давал прежний адрес `http://100.108.92.92/o/1234` (27
символов): переход на имя размер кода **не изменил**. Запас до 42 символов
покрывает семизначные номера — он не кончится.

Если вы поменяете `LABEL_BASE_URL` на что-то длинное, страницы печати
скажут об этом жёлтой плашкой **до** печати, а не после того, как этикетки
наклеены.

### Что делать, если адрес Pi в Tailscale изменился

Программа не пострадает: адрес нигде не хранится, QR рисуется в момент
печати. Пострадают только уже наклеенные этикетки — в них старый адрес.

**1. Поправить настройку** в `/opt/lifteam/.env` (если строки там нет —
дописать её; встроенное значение подходит только для прежнего имени):

```ini
LABEL_BASE_URL=http://новое-имя.ts.net
```

**2. Перезапустить приложение** — обязательно: из этой же настройки на
старте собираются `ALLOWED_HOSTS` и `CSRF_TRUSTED_ORIGINS`. Без перезапуска
отсканированный код упрётся в «400 Bad Request»:

```bash
sudo systemctl restart lifteam
```

**3. Перепечатать этикетки**, напечатанные со старым адресом. Пачкой это
делается быстро: «Радиодетали → отметить → Этикетки», «Кассетницы →
Этикетки на кассетницу».

**Чтобы этого не случилось.** Адрес `100.x` и имя MagicDNS закреплены
за узлом и переживают перезагрузки и переустановку самого Tailscale.
Меняются они, когда узел удаляют из тайнета и заводят заново. Поэтому
при любых работах на Pi **не удаляйте узел в панели Tailscale**,
а переавторизуйте существующий:

```bash
sudo tailscale up --force-reauth
```

И ещё одна необязательная строка — `WARRANTY_MONTHS`:

```ini
WARRANTY_MONTHS=12
```

Срок гарантии на ремонт в месяцах; отсчитывается от даты завершения заказа.
По умолчанию 12. Значение `0` отключает гарантию — отметки о ней просто
перестают показываться. Параметр действует сразу на все заказы, в том числе
на завершённые раньше: гарантия нигде не хранится, а вычисляется от даты.

### Реквизиты организации

Название фирмы, ИНН, КПП, адрес, телефоны и подписанта нужно один раз
вписать в программе: **Администрирование → Реквизиты**. Они печатаются
в шапке и в подписи актов приёма и выполненных работ.

Через `.env` это не задаётся намеренно: менять реквизиты приходится
владельцу — переехали, сменился директор, — и лазить для этого по SSH
он не должен.

Пока реквизиты не заполнены, акты печатаются без шапки. Это не ошибка
и печати не мешает, но заказчику такой документ лучше не отдавать.

### Оповещения на почту

Программа умеет писать заказчику о готовности заказа и кладовщикам —
о деталях, ушедших в дефицит. **По умолчанию отправка выключена:** события
копятся в очереди, но письма не уходят. Так сделано намеренно — сначала
посмотрите в разделе «Оповещения», что программа собирается отправлять,
и только потом включайте.

Чтобы письма пошли, заполните почтовые параметры (`EMAIL_HOST_USER`,
`EMAIL_HOST_PASSWORD`, `DEFAULT_FROM_EMAIL`) и добавьте:

```ini
NOTIFICATIONS_ENABLED=True
```

Письма **заказчикам** включаются отдельно — это переписка от лица фирмы
с внешними людьми, и она не должна заработать сама после обновления:

```ini
NOTIFY_CLIENTS=True
```

Для Яндекса в `EMAIL_HOST_PASSWORD` нужен **пароль приложения**, а не пароль
от почты: обычный пароль SMTP не примет.

Проверить, не отправляя ничего:

```bash
sudo -u lifteam /opt/lifteam/venv/bin/python /opt/lifteam/manage.py send_notifications --dry-run
```

Отправку по расписанию (раз в 5 минут) включает таймер:

```bash
sudo cp /opt/lifteam/deploy/lifteam-notify.{service,timer} /etc/systemd/system/
```

```bash
sudo systemctl daemon-reload && sudo systemctl enable --now lifteam-notify.timer
```

Таймер можно включить заранее: пока `NOTIFICATIONS_ENABLED=False`, команда
ничего не делает.

### Задолженности

Программа умеет каждое утро смотреть, кто не заплатил, и класть в очередь
две вещи: **сводку бухгалтеру** и, отдельно, **напоминание заказчику**.

Долг считается просроченным через 14 дней после **даты счёта** — не после
приёма заказа: пока счёт не выставлен, требовать оплату не за что. Срок
меняется:

```ini
DEBT_OVERDUE_DAYS=14
```

**Сводка бухгалтеру и администратору** включена сразу — это внутреннее
письмо. Одним списком: кто, по какому счёту, сколько и на сколько дней
просрочил, плюс отдельным разделом заказы, которые отгрузили, а счёт
так и не выставили. Повторяется не чаще раза в неделю, поэтому ежедневный
запуск не превращается в ежедневное письмо.

**Напоминания самим заказчикам выключены** и требуют вдобавок включённого
`NOTIFY_CLIENTS`: это требование денег от лица фирмы, и начинаться само
собой после обновления оно не должно. Когда решите включать:

```ini
NOTIFY_DEBTS=True
```

Одному заказчику по одному заказу пишется не чаще раза в неделю. В письме
называется **остаток**, а не полная стоимость: часть денег заказчик мог уже
перевести, и требовать их повторно — верный способ испортить отношения.
Заказы, по которым не осталось ни рубля, пропускаются вовсе.

Чтобы остаток считался, поступившие деньги нужно вносить в карточку заказа
(раздел «Оплаты», доступен бухгалтеру и администратору). Пока их не вносят,
долгом считается вся стоимость — как и раньше.

Посмотреть, что попало бы в очередь, ничего не отправляя:

```bash
sudo -u lifteam /opt/lifteam/venv/bin/python /opt/lifteam/manage.py debt_reminders --dry-run
```

Проверку по расписанию (будни, 9 утра) включает таймер:

```bash
sudo cp /opt/lifteam/deploy/lifteam-debts.{service,timer} /etc/systemd/system/
```

```bash
sudo systemctl daemon-reload && sudo systemctl enable --now lifteam-debts.timer
```

Сама команда ничего не отправляет — только наполняет очередь; отправляет
её таймер оповещений выше. Выходные пропускаются намеренно: письмо о
деньгах, пришедшее в субботу, раздражает и ничего не ускоряет.

Чтобы сводка дошла, у бухгалтера в карточке должна быть заполнена почта
(«Администрирование → Пользователи»), а роль — «Бухгалтер» или
«Администратор». Кладовщикам этот список не уходит.

### Просроченные заказы

Программа умеет каждый день смотреть, не завис ли заказ в одном статусе
дольше разумного срока, и предупреждать об этом менеджера по ремонту
и администратора. Заказчику это оповещение никогда не уходит — это
внутренняя кухня.

«Завис» — значит с заказом давно ничего не делали: не переводили в другой
статус, не списывали деталь. Порог свой на каждый промежуточный статус,
меняется в `.env`:

```ini
ORDER_OVERDUE_DAYS_ACCEPTED=2
ORDER_OVERDUE_DAYS_DIAGNOSTIC=3
ORDER_OVERDUE_DAYS_REPAIR=7
ORDER_OVERDUE_DAYS_READY_FOR_SHIPMENT=5
```

У статусов «Отгружен» и «Ремонт невозможен» порога нет — это завершённые
состояния, а не зависшие.

Оповещение приходит один раз при первом пересечении порога, а затем,
пока заказ не сдвинется со статуса, повторяется не чаще раза в неделю
(эскалация):

```ini
ORDER_OVERDUE_ESCALATION_DAYS=7
```

Посмотреть, что попало бы в очередь, ничего не отправляя:

```bash
sudo -u lifteam /opt/lifteam/venv/bin/python /opt/lifteam/manage.py order_overdue_check --dry-run
```

Проверку по расписанию (каждый день в 9:15) включает таймер:

```bash
sudo cp /opt/lifteam/deploy/lifteam-order-overdue.{service,timer} /etc/systemd/system/
```

```bash
sudo systemctl daemon-reload && sudo systemctl enable --now lifteam-order-overdue.timer
```

Сама команда ничего не отправляет — только наполняет очередь; отправляет
её таймер оповещений выше. Чтобы оповещение дошло, у менеджера по ремонту
или администратора в карточке должна быть заполнена почта или включён
мессенджер («Администрирование → Пользователи»).

### Российский корневой сертификат

**Делается один раз и до настройки Т-Банка и MAX.** Без него оба канала
молча не работают.

Выглядит это так: в очереди оповещений висит

```
MAX недоступен: [SSL: CERTIFICATE_VERIFY_FAILED] certificate verify failed:
unable to get local issuer certificate
```

а команда выписки отвечает то же самое про Т-Банк. Сеть при этом в порядке,
токен верный, и по тексту непонятно, что чинить.

Причина. Сайты российских сервисов подписаны сертификатом **НУЦ Минцифры**,
а его нет ни в одном стандартном наборе корневых сертификатов — ни в
`ca-certificates` Debian, ни внутри Python. Проверка сертификата сервера
падает, и приложение видит это как «сервис недоступен».
`apt install --reinstall ca-certificates` не помогает: там этого
сертификата нет и не будет.

**1. Скачать сертификат.** С обычного компьютера, где сайт открывается,
откройте https://www.gosuslugi.ru/crt и возьмите **корневой сертификат
Минцифры в формате PEM** (файл вида `russian_trusted_root_ca_pem.crt`).
Вариант «ГОСТ» для наших задач не нужен: MAX и Т-Банк работают по обычному
RSA.

**2. Перенести файл на Pi.** Проще всего вставкой через терминал — тогда
не нужно ни `scp`, ни флешки. На Pi выполните:

```bash
cat > ~/russian_trusted_root_ca.crt
```

Курсор уйдёт на пустую строку — вставьте туда всё содержимое скачанного
файла целиком, вместе со строками `-----BEGIN CERTIFICATE-----` и
`-----END CERTIFICATE-----`, и нажмите **Ctrl+D**.

Проверьте, что файл читается как сертификат:

```bash
openssl x509 -in ~/russian_trusted_root_ca.crt -noout -subject
```

Ответ должен содержать `Russian Trusted Root CA`. Если вместо этого ошибка
разбора — файл сохранён не полностью или это не PEM.

**3. Положить в системный набор.** Расширение обязательно `.crt`, иначе
`update-ca-certificates` файл не заметит:

```bash
sudo cp ~/russian_trusted_root_ca.crt /usr/local/share/ca-certificates/
```

```bash
sudo update-ca-certificates
```

В ответе должно быть `1 added`. Если `0 added` — файл лежит не в том
каталоге или с другим расширением.

**4. Перезапустить приложение**, чтобы уже открытые процессы взяли
обновлённый набор:

```bash
sudo systemctl restart lifteam
```

**Проверка.** Соединение с сервисом должно проверяться без ошибок:

```bash
openssl s_client -connect platform-api2.max.ru:443 -brief < /dev/null
```

В выводе нужна строка `Verify return code: 0 (ok)`. Для банка то же самое
с `business.tbank.ru:443`.

Отдельно настраивать Python не нужно: он берёт сертификаты из системного
набора OpenSSL, того же, который обновляет `update-ca-certificates`.

**Чего делать нельзя.** В интернете советуют «отключить проверку
сертификата» — `verify=False`, `ssl._create_unverified_context` и подобное.
Так делать не нужно: в тех же запросах уходит токен бота и токен банка,
а без проверки сертификата их может прочитать кто угодно между Pi и
сервисом.

### Поступления из Т-Банка

Программа умеет сама забирать выписку по расчётному счёту и показывать
поступления рядом с долгами по заказам — чтобы каждую оплату не набирать
руками и чтобы напоминание не уходило тому, кто уже заплатил.

**Программа только читает выписку.** Ни одного метода, двигающего деньги,
в ней нет. Токен в банке выдавайте с правами **только на просмотр
операций** — большего ей не нужно, а меньше прав означает меньше ущерба,
если Pi попадёт в чужие руки.

**1. Получить токен.** Личный кабинет Т-Бизнеса → Настройки → Токены API.
Создайте токен, разрешив ему только чтение выписки. Токен — это пароль
к сведениям о ваших деньгах: не пересылайте его в переписке и не храните
нигде, кроме `.env` на самом Pi.

**2. Записать его в `.env`:**

```ini
TBANK_TOKEN=сюда-токен-из-кабинета
```

**3. Узнать номер расчётного счёта:**

```bash
sudo -u lifteam /opt/lifteam/venv/bin/python /opt/lifteam/manage.py tbank_statement --accounts
```

**4. Записать номер в `.env`:**

```ini
TBANK_ACCOUNT=40802810700006096146
```

**5. Проверить, что выписка читается**, ничего не сохраняя:

```bash
sudo -u lifteam /opt/lifteam/venv/bin/python /opt/lifteam/manage.py tbank_statement --dry-run
```

Команда напечатает поступления за последний месяц. Если список пуст,
а деньги за этот месяц приходили — пришлите мне вывод команды: значит,
банк называет поля выписки не так, как ожидает программа, и разбор надо
поправить.

**6. Включить загрузку по расписанию** (будни, раз в час с 8 до 19):

```bash
sudo cp /opt/lifteam/deploy/lifteam-tbank.{service,timer} /etc/systemd/system/
```

```bash
sudo systemctl daemon-reload && sudo systemctl enable --now lifteam-tbank.timer
```

Дальше поступления появляются в разделе «Поступления» (виден бухгалтеру
и администратору), а на дашборде — сколько их ждёт разнесения. Деньги
по заказам разносит человек кнопкой: программа только подсказывает заказ
по номеру счёта, номеру заказа в назначении платежа или ИНН плательщика.

Пока `TBANK_TOKEN` пустой, раздел просто не пополняется, и всё остальное
работает как раньше.

### Выставление счетов через Т-Банк

Программа умеет собрать счёт по заказу и выставить его в Т-Банке; банк
отправит его заказчику на почту, а ссылка на PDF останется в заказе.

**Номер счёта задаёте вы.** Банк своего номера не подставляет — берёт тот,
что пришёл от программы. Значит, сквозной ряд с теми счетами, что вы
выставляете руками в личном кабинете, держите вы: программа их не видит.
Номер на странице открыт для правки, сверяйте его перед каждой отправкой.

**Отправка не включается сама.** Мало токена — нужен отдельный выключатель.

**1. Дать токену право выставлять счета.** В личном кабинете Т-Бизнеса
у токена, который вы завели для выписки, должно быть разрешение на
выставление счетов контрагентам. Если такого права нет, банк ответит
отказом, а программа покажет его текст.

**2. Включить в `.env`:**

```ini
TBANK_INVOICE_ENABLED=True
```

**3. Задать, с какого номера начинать**, если ряд ведёте с определённого
числа (программа возьмёт больший из этого числа и своего последнего):

```ini
TBANK_INVOICE_NUMBER_START=944
```

**4. При необходимости — срок оплаты, единицу и НДС:**

```ini
TBANK_INVOICE_DUE_DAYS=14
```

```ini
TBANK_INVOICE_VAT=None
```

`None` здесь означает «без НДС» — так это называет банк, и на УСН нужно
именно оно.

Дальше в карточке заказа появляется кнопка «Счёт» (у бухгалтера и
администратора). Она ведёт на страницу, где видно всё, что уйдёт в банк:
плательщик, строки с ценами, итог, номер и даты. Отправка — отдельным
нажатием с подтверждением.

**Первый счёт выставьте на небольшую сумму и на свой собственный адрес**,
без адреса заказчика: так вы увидите, что банк принимает формат, ничем
не рискуя. Отменить выставленный счёт из программы нельзя — только
в личном кабинете банка.

Если банк ответит отказом, его текст сохранится в заказе и покажется
при следующем заходе на страницу. Пришлите мне этот текст — по нему
видно, какое поле не понравилось.

### Оповещения в MAX

Почта на телефоне часто молчит до следующего открытия ящика, а сообщение
в мессенджере видно сразу. Дефицит деталей программа умеет присылать
в MAX — тем же кладовщикам и администраторам, дополнительно к письмам.
Заказчикам в MAX ничего не уходит: у них нет и не должно быть бота фирмы.

Настройка занимает четыре шага и делается один раз.

**1. Завести бота.** В приложении MAX найдите `@MasterBot`, отправьте ему
`/create` и следуйте вопросам — он спросит имя бота и выдаст токен
(длинная строка). Токен — это пароль: кто им владеет, тот пишет от имени
бота. Никому его не пересылайте.

**2. Вписать токен** в `/opt/lifteam/.env`:

```ini
MAX_BOT_TOKEN=выданный_masterbot_токен
NOTIFY_MAX=True
```

**3. Узнать, кому писать.** Бот не может написать человеку первым: пока
сотрудник сам не напишет боту, отправлять ему некуда. Попросите каждого
найти бота в MAX и отправить ему любое сообщение, затем выполните:

```bash
sudo -u lifteam /opt/lifteam/venv/bin/python /opt/lifteam/manage.py max_updates
```

Команда покажет таблицу: числовой ID и имя в MAX.

**4. Вписать ID сотрудникам** — в программе, «Администрирование →
Пользователи → Изменить → ID в MAX». У кого поле пустое, тот получает
только письма.

Вместо личных сообщений можно слать всё в один общий чат: добавьте бота
в чат, найдите идентификатор чата в выводе `max_updates` (строка «Чаты, где
бот состоит») и укажите его:

```ini
MAX_GROUP_CHAT_ID=-98765
```

Тогда оповещение уходит один раз в чат, а не каждому кладовщику отдельно;
личные ID при этом не используются.

Отправку выполняет тот же таймер, что и письма, — отдельно ничего включать
не нужно. Проверить, что канал живой:

```bash
sudo -u lifteam /opt/lifteam/venv/bin/python /opt/lifteam/manage.py send_notifications --dry-run
```

В строках очереди канал виден и в разделе «Оповещения»: у сообщений MAX
стоит соответствующая метка, а вместо номера показывается имя сотрудника.

Если MAX перестал принимать сообщения после смены адреса их API (такое уже
было летом 2026, когда отключили `platform-api.max.ru`), новый адрес
задаётся, не трогая программу:

```ini
MAX_API_URL=https://новый-адрес
```

### Оповещения в Telegram

Устроены так же, как MAX, и работают одновременно с ним: можно включить
оба канала, один или ни одного. Уходит то же самое — дефицит деталей
сотрудникам.

**Сначала проверьте, доступен ли Telegram с самого Pi.** Если сеть его
не пропускает, сообщения будут копиться в очереди с ошибкой — вреда нет,
но и толку тоже:

```bash
curl -s -o /dev/null -w '%{http_code}\n' https://api.telegram.org
```

Ответ `200` — доступен. Пусто или ошибка — канал включать не стоит.

**1. Завести бота.** В Telegram найдите `@BotFather`, отправьте `/newbot`
и ответьте на два вопроса (имя и логин бота). В ответ придёт токен вида
`123456789:AAExxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx`. Токен — это пароль:
кто им владеет, тот пишет от имени бота, никому его не пересылайте.

**2. Вписать токен** в `/opt/lifteam/.env`:

```ini
TELEGRAM_BOT_TOKEN=выданный_botfather_токен
NOTIFY_TELEGRAM=True
```

**3. Узнать, кому писать.** Попросите каждого сотрудника найти бота
в Telegram, нажать «Запустить» (`/start`) и отправить любое сообщение,
затем выполните:

```bash
sudo -u lifteam /opt/lifteam/venv/bin/python /opt/lifteam/manage.py telegram_updates
```

Команда покажет `chat_id` и имя. Telegram хранит события **только сутки** —
если сотрудник написал боту неделю назад, попросите написать ещё раз.

**4. Вписать chat_id сотрудникам** — «Администрирование → Пользователи →
Изменить → ID в Telegram».

Общая группа вместо личных сообщений: добавьте бота в группу, напишите
там что-нибудь, посмотрите идентификатор в выводе `telegram_updates`
(у групп он отрицательный) и укажите:

```ini
TELEGRAM_GROUP_CHAT_ID=-1001234567890
```

Отправку выполняет тот же таймер. Если Telegram доступен только через
зеркало или свой Bot API server, адрес меняется, не трогая программу:

```ini
TELEGRAM_API_URL=https://адрес-зеркала
```

Сохранить в nano: `Ctrl+O`, `Enter`, затем `Ctrl+X`.

Закройте файл от посторонних — в нём ключ приложения:

```bash
sudo chmod 600 /opt/lifteam/.env && sudo chown lifteam:lifteam /opt/lifteam/.env
```

## 5. База данных и администратор

```bash
cd /opt/lifteam
```

```bash
sudo -u lifteam venv/bin/python manage.py migrate --settings=lifteam.settings_pi
```

```bash
sudo -u lifteam venv/bin/python manage.py init_cells --settings=lifteam.settings_pi
```

По умолчанию заводятся 12 кассетниц по 64 ячейки (восемь рядов по восемь).
Если на полке стоят другие, раскладку можно задать сразу — числом ячеек
на каждый ряд, сверху вниз:

```bash
sudo -u lifteam venv/bin/python manage.py init_cells --cabinets 3 \
    --layout "16,16,8,8,4,4,2" --settings=lifteam.settings_pi
```

Уже заведённые кассетницы команда не трогает: повторный запуск ничего
не ломает, а перекроить существующую можно потом в самой программе —
«Радиодетали → Кассетницы».

```bash
sudo -u lifteam venv/bin/python manage.py collectstatic --noinput --settings=lifteam.settings_pi
```

Флаг `--settings` указывается в каждой команде намеренно. `sudo` по умолчанию
очищает переменные окружения, поэтому заданный заранее `DJANGO_SETTINGS_MODULE`
до приложения не дойдёт, и команда молча выполнится с настройками для
разработки — с `DEBUG=True`.

Создайте администратора:

```bash
sudo -u lifteam venv/bin/python manage.py create_admin --username admin --name "Администратор" --password "временный" --settings=lifteam.settings_pi
```

Сразу задайте настоящий пароль — интерактивно, чтобы он не попал в историю
команд оболочки:

```bash
sudo -u lifteam venv/bin/python manage.py changepassword admin --settings=lifteam.settings_pi
```

Стандартную пару `admin` / `admin123` в офисе не оставляйте: она указана
в документации проекта и известна всем, кто видел репозиторий.

## 7. Удалённый доступ через интернет

У вас серый IP: провайдер не выдаёт внешний адрес, поэтому проброс портов
на роутере не поможет — снаружи к нему не подключиться. Обходится через
Tailscale: это VPN на базе WireGuard, который сам устанавливает соединение
через NAT провайдера.

### На Raspberry Pi

```bash
curl -fsSL https://tailscale.com/install.sh | sh
```

Подключать устройство лучше **ключом авторизации**, а не ссылкой из терминала.
Команда `sudo tailscale up` выводит ссылку и ждёт подтверждения в браузере;
на практике это ломается: ссылка одноразовая и живёт недолго, любое нажатие
`Ctrl+C` её аннулирует (в логе появляется `http 410: auth path not found`),
а при уже открытой в браузере сессии Tailscale она отдаёт `403`. Ключ от
всего этого не зависит.

Создайте ключ в панели управления — [login.tailscale.com/admin/settings/keys](https://login.tailscale.com/admin/settings/keys),
кнопка `Generate auth key`. Флаг `Reusable` **не включайте**: одноразовый ключ
после подключения станет недействительным, и его утечка через историю команд
ничего не даст.

Подключите устройство, подставив свой ключ:

```bash
sudo tailscale up --authkey=ВАШ-КЛЮЧ
```

Проверьте:

```bash
tailscale status
```

Появится строка с адресом вида `100.x.x.x` и именем устройства. Полное имя:

```bash
tailscale status --json | grep -i '"DNSName"'
```

Добавьте в `ALLOWED_HOSTS` в файле `.env` и адрес `100.x.x.x`, и полное имя
(без точки в конце):

```bash
sudo -u lifteam nano /opt/lifteam/.env
```

```bash
sudo systemctl restart lifteam
```

Чтобы авторизация не истекала через несколько месяцев, отключите срок
действия ключа для этого устройства в панели управления Tailscale
(Machines → устройство → Disable key expiry).

### На компьютерах, планшетах и телефонах

Установите клиент Tailscale и войдите в ту же учётную запись:

- Windows и macOS — с сайта tailscale.com
- Android — Google Play
- iPhone и iPad — App Store

После этого приложение открывается по адресу `http://lifteam.ваша-сеть.ts.net`
из любой точки, где есть интернет. В офисе работает и обычный локальный
адрес — Tailscale этому не мешает.

Проверять удалённый доступ нужно **с устройства вне офисной сети** — например
с телефона по мобильному интернету, выключив Wi-Fi. Проверка с ноутбука,
стоящего в той же комнате, ничего не доказывает: он и так открывает
приложение по локальному адресу.

> **Известная проблема на Windows.** Бывает, что клиент показывает
> `Connected` и `tailscale ping` получает ответ, но обычный трафик через
> адаптер не идёт: браузер выдаёт `ERR_NETWORK_ACCESS_DENIED`
> («Доступ в Интернет заблокирован»), `ping` — `Общий сбой` (код 11050).
> Значит виртуальный адаптер поднят, но маршруты через него не работают.
> Обычно лечится перезагрузкой компьютера. На Android и iOS такого не
> наблюдалось. В офисе это не мешает — там используется локальный адрес.

### Почему не публичный доступ

Через Tailscale приложение не видно из интернета: подключиться могут только
устройства вашей учётной записи, трафик шифруется. Открывать приложение
наружу означало бы, что его начнут находить сканеры и подбирать пароли —
при отсутствии HTTPS и двухфакторной аутентификации это плохая идея.

Если доступ понадобится с чужого устройства, куда VPN не поставить,
альтернатива — Cloudflare Tunnel, но там придётся отдельно заниматься
аутентификацией.

## 8. Резервное копирование

Копии базы делаются автоматически, ежедневно в 3:30.

```bash
sudo cp /opt/lifteam/deploy/lifteam-backup.service /etc/systemd/system/
```

```bash
sudo cp /opt/lifteam/deploy/lifteam-backup.timer /etc/systemd/system/
```

```bash
sudo systemctl daemon-reload
```

```bash
sudo systemctl enable --now lifteam-backup.timer
```

Проверьте, что расписание встало:

```bash
systemctl list-timers lifteam-backup.timer
```

Разовый запуск для проверки:

```bash
sudo systemctl start lifteam-backup
```

```bash
journalctl -u lifteam-backup -n 20
```

```bash
ls -la /opt/lifteam/backups/
```

### Копия за пределами устройства

Копии в `/opt/lifteam/backups/` лежат на том же диске, что и база. От ошибки
оператора это защищает, от отказа диска или кражи — нет.

Официального клиента Яндекс.Диска под ARM не существует, поэтому используем
`rclone` — он умеет Яндекс.Диск и работает на Pi:

```bash
sudo apt install -y rclone
```

```bash
sudo -u lifteam RCLONE_CONFIG=/opt/lifteam/rclone.conf rclone config
```

В диалоге: `n` (новый remote) → имя `yandex` → тип `yandex` → далее по
подсказкам, авторизация через браузер.

Затем включите выгрузку — откройте файл службы:

```bash
sudo nano /etc/systemd/system/lifteam-backup.service
```

Раскомментируйте строку (уберите `#` в начале):

```ini
Environment=LIFTEAM_RCLONE_REMOTE=yandex:LiftTeam/backups
```

```bash
sudo systemctl daemon-reload && sudo systemctl start lifteam-backup
```

```bash
journalctl -u lifteam-backup -n 20
```

Конфигурация rclone намеренно лежит в `/opt/lifteam`, а не в домашнем
каталоге: служба запускается с `ProtectHome=true` и до `/home` не достучится.

### Проверка восстановления

Бэкап, который ни разу не разворачивали, — это не бэкап, а надежда.
Проверьте хотя бы раз, а потом повторяйте раз в несколько месяцев.

Список копий:

```bash
cd /opt/lifteam && sudo -u lifteam venv/bin/python manage.py restore_db --list --settings=lifteam.settings_pi
```

Безопасная проверка на копии, без риска для рабочих данных:

```bash
sudo cp $(ls -t /opt/lifteam/backups/db_*.sqlite3 | head -1) /tmp/test.sqlite3
```

```bash
sqlite3 /tmp/test.sqlite3 "PRAGMA integrity_check; SELECT COUNT(*) FROM core_sparepart;"
```

```bash
rm /tmp/test.sqlite3
```

Если понадобится настоящее восстановление:

```bash
sudo systemctl stop lifteam
```

```bash
cd /opt/lifteam && sudo -u lifteam venv/bin/python manage.py restore_db --settings=lifteam.settings_pi
```

```bash
sudo systemctl start lifteam
```

Команда проверяет копию до того, как трогать рабочую базу, а текущую
отставляет в сторону с меткой времени — ошибочное восстановление обратимо.

## 9. Обновление

### Из веб-интерфейса

Раздел «Обновление» в меню, доступен администратору. Показывает установленную
версию, список изменений и кнопку обновления, а также историю версий с
возможностью отката.

Чтобы это заработало, нужно установить привилегированную часть. Приложение
работает от пользователя `lifteam` и не может перезапускать службу — для
этого нужны права root. Давать веб-приложению `sudo` нельзя: тогда любая
уязвимость в нём означала бы полный доступ к устройству. Поэтому приложение
лишь создаёт файл-заявку, а работу выполняет отдельная служба.

Установите скрипт **вне каталога приложения**:

```bash
sudo cp /opt/lifteam/deploy/lifteam-update-runner.sh /usr/local/sbin/lifteam-update
```

```bash
sudo chown root:root /usr/local/sbin/lifteam-update && sudo chmod 755 /usr/local/sbin/lifteam-update
```

Расположение и владелец здесь принципиальны. Если оставить скрипт в
`/opt/lifteam`, где владелец — пользователь приложения, то взломщик подменит
его содержимое и получит выполнение команд от root.

Установите службу, реагирующую на заявку:

```bash
sudo cp /opt/lifteam/deploy/lifteam-update.path /opt/lifteam/deploy/lifteam-update.service /etc/systemd/system/
```

```bash
sudo systemctl daemon-reload
```

```bash
sudo systemctl enable --now lifteam-update.path
```

Проверить, что слежение включено:

```bash
systemctl status lifteam-update.path --no-pager
```

Ход обновления виден в журнале:

```bash
journalctl -u lifteam-update -f
```

> Обновление из интерфейса не заменяет доступ по SSH. Если новая версия
> не запустится, чинить придётся из командной строки — неработающая программа
> не может показать страницу обновления.

### Из командной строки

```bash
sudo /opt/lifteam/deploy/update.sh
```

Скрипт по порядку: делает копию базы, останавливает приложение, забирает
изменения из GitHub, ставит зависимости, применяет миграции, пересобирает
статику и запускает приложение обратно. В конце проверяет, что служба
действительно поднялась.

Если на каком-то шаге произойдёт ошибка, приложение останется остановленным —
это сделано намеренно, чтобы оно не работало со схемой базы, не совпадающей
с кодом. Скрипт выведет команды для возврата к предыдущей версии.

> Скрипт `update.sh` в корне проекта для сервера не подходит: он делает
> `git reset --hard` и на этом заканчивает — без копии базы, миграций
> и перезапуска службы.

## 10. Надёжность работы

### Сохранение журнала между перезагрузками

**Сделайте это сразу.** По умолчанию Raspberry Pi OS хранит журнал systemd
в оперативной памяти и стирает при каждой перезагрузке. Это уже приводило
к тому, что причину ошибки 500 установить не удалось: перезагрузка починила
приложение и одновременно уничтожила единственное свидетельство.

```bash
sudo mkdir -p /var/log/journal
```

```bash
sudo systemd-tmpfiles --create --prefix /var/log/journal
```

Ограничим размер, чтобы журнал не занял диск:

```bash
sudo sh -c 'printf "[Journal]\nStorage=persistent\nSystemMaxUse=500M\nMaxRetentionSec=1month\n" > /etc/systemd/journald.conf.d/lifteam.conf'
```

```bash
sudo systemctl restart systemd-journald
```

Перенести накопленные записи в новый каталог. Без этого шага journald
продолжит писать в память до следующей загрузки, а каталог останется пустым:

```bash
sudo journalctl --flush
```

Проверка — каталог должен занимать заметный объём, а не быть пустым:

```bash
sudo du -sh /var/log/journal/
```

### Автоматический перезапуск при зависании

В службе задан перезапуск при сбое, но он срабатывает, только когда процесс
завершился. Зависший процесс продолжает висеть в памяти, для systemd он
исправен, и служба остаётся «работающей», пока сотрудники видят ошибку.
Отдельная проверка раз в пять минут закрывает этот случай.

```bash
sudo cp /opt/lifteam/deploy/healthcheck.sh /usr/local/sbin/lifteam-healthcheck
```

```bash
sudo chown root:root /usr/local/sbin/lifteam-healthcheck && sudo chmod 755 /usr/local/sbin/lifteam-healthcheck
```

```bash
sudo cp /opt/lifteam/deploy/lifteam-healthcheck.service /opt/lifteam/deploy/lifteam-healthcheck.timer /etc/systemd/system/
```

```bash
sudo systemctl daemon-reload
```

```bash
sudo systemctl enable --now lifteam-healthcheck.timer
```

Что делала проверка:

```bash
journalctl -u lifteam-healthcheck -n 30 --no-pager
```

Проверка реагирует только на полное молчание приложения. Если оно отвечает
ошибкой 500, перезапуск не поможет — причину надо искать в логах, поэтому
служба намеренно не трогает работающий процесс.

## 11. Если что-то не работает

Ошибки приложения с трассировками — отдельный файл, он переживает
перезагрузку независимо от настроек журнала:

```bash
tail -50 /opt/lifteam/logs/errors.log
```

Логи приложения:

```bash
journalctl -u lifteam -f
```

Логи резервного копирования:

```bash
journalctl -u lifteam-backup -n 50
```

Логи веб-сервера:

```bash
sudo tail -f /var/log/nginx/error.log
```

**`400 Bad Request`** — адрес, по которому вы открываете приложение, не указан
в `ALLOWED_HOSTS`. Добавьте его в `.env` и выполните `sudo systemctl restart lifteam`.

**`502 Bad Gateway`** — приложение не запущено. `systemctl status lifteam`
покажет причину.

**Служба не стартует, ошибка про путь в `ExecStart`** — в файле оказались
переводы строк Windows:

```bash
sudo sed -i 's/\r$//' /opt/lifteam/deploy/*.sh
```

**Остатки на складе не обновляются без перезагрузки страницы** — не проходит
WebSocket-соединение. Проверьте, что в конфигурации nginx есть секция
`location /ws/` с заголовками `Upgrade`, и перезагрузите nginx.

**`database is locked`** — не должно возникать, база работает в режиме WAL.
Проверить:

```bash
sqlite3 /opt/lifteam/db.sqlite3 "PRAGMA journal_mode;"
```

Ответ должен быть `wal`.

**Нет места на диске** — вероятно, накопились копии базы. Глубина хранения
задаётся параметром `KEEP_DAYS` в `deploy/backup.sh`:

```bash
du -sh /opt/lifteam/backups/
```

## Что не входит в эту установку

**Печать с планшетов и телефонов не заработает.** Этикетки печатаются через
диалог браузера, поэтому печатать может только устройство, к которому
подключён принтер. Для печати с мобильных нужна доработка — печать на стороне
сервера через CUPS.

**HTTPS не настраивается.** При доступе через Tailscale трафик шифруется
самим VPN, а в локальной сети сертификат для адреса вида `192.168.1.50`
получить негде. Если приложение когда-либо будет открыто в интернет,
HTTPS станет обязательным.

**Интерфейс не адаптирован под телефоны.** Сетка кассетниц рисуется во всю
высоту экрана, и при полусотне ячеек на смартфоне она будет мелкой.
С планшета работать удобно.
