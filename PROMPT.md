# ПРОМПТ: LiftTeam

Правила работы над проектом для ИИ-агента. Этот файл имеет приоритет над
текстом отдельных задач при противоречиях — но если противоречие возникло,
скажи об этом явно, а не выбирай молча.

## Контекст

LiftTeam — система учёта заказов на ремонт лифтового оборудования и склада
радиодеталей. Работает в офисе на Raspberry Pi 4, доступ сотрудников —
локально и через интернет по Tailscale, с компьютеров, планшетов и телефонов.

Репозиторий: https://github.com/yachtsman13/Lifteam (ветка `main`)

## Источник кода

**Исходный код — рабочая копия репозитория.** Читай файлы прямо из неё.

- Не восстанавливай код по памяти о прошлых сессиях — он меняется между ними.
- Не предполагай содержимое файла, не прочитав его. Особенно это касается
  моделей: `core/models.py` — источник истины о том, какие поля существуют.
- Перед изменением незнакомой области прочитай её целиком, а не только строки
  вокруг правки.

Если работаешь без доступа к репозиторию (например, в чате по присланному
архиву) — это исключение, а не норма; в таком случае явно предупреди, что
сверить код с актуальным состоянием не можешь.

## Порядок работы

### 1. Понять текущее состояние

1. `CHANGELOG.md` — верхняя запись показывает текущую версию и что менялось
   последним.
2. `core/models.py` — состав сущностей и полей.
3. Файлы той области, которую предстоит менять.

### 2. Внести изменения

1. Отредактировать нужные файлы.
2. Написать или обновить тесты в `core/tests.py` — новая логика без теста
   не считается законченной.
3. Прогнать весь набор: `python manage.py test`. Все тесты должны проходить.
4. Проверить в браузере то, что видно пользователю: вёрстку, форму, этикетку.
   Этикетки проверять измерением элементов, а не на глаз — лист 43×25 мм, за
   его пределы ничего выходить не должно.

### 3. Сдать работу

1. Обновить версию: `update_version.sh <версия>` (Linux/macOS) или
   `update_version.bat <версия>` (Windows). Скрипт проходит по служебным
   файлам, `core/` и `lifteam/`.
2. Добавить запись в `CHANGELOG.md` **вручную** — скрипт версии его намеренно
   не трогает (глобальная замена переписала бы заголовки всех прошлых
   выпусков и уничтожила историю).
3. Обновить `README.md` / `DEPLOY.md` / `TZ.md`, если изменилось то, что там
   описано.
4. Обновить этот файл, если изменился сам процесс работы.
5. Коммит и `git push origin main`.

После пуша обновление на Raspberry Pi выполняет администратор кнопкой в
разделе «Обновление» внутри приложения — отдельно ничего собирать и никуда
присылать не нужно.

## Как писать в CHANGELOG

Записи читает владелец проекта, а не разработчик. Поэтому:

- по-русски, без жаргона и названий файлов;
- сначала что изменилось для человека, потом — почему, если причина неочевидна;
- если исправлена ошибка, из-за которой что-то работало неверно, — сказать,
  что именно было не так, а не только что починили.

## Стек

Python 3.12, Django 5.1, DRF, Django Channels (ASGI/Daphne), Bootstrap 5,
vanilla JS. Библиотеки: `openpyxl` (Excel), `qrcode`, `python-barcode`,
`Pillow`.

База: SQLite в режиме WAL — и в разработке, и на Raspberry Pi. Вариант с
PostgreSQL и Redis существует в `settings_production.py` для запуска в Docker,
но в работе не используется.

Настройки:

| Файл | Где применяется |
|---|---|
| `lifteam/settings.py` | разработка |
| `lifteam/settings_pi.py` | Raspberry Pi (рабочая установка) |
| `lifteam/settings_production.py` | Docker, не используется |

## Ключевые правила

1. Авторизация по логину: `Employee.USERNAME_FIELD = 'username'`.
2. Роли: `admin`, `warehouse`, `repair_manager`, `accountant`. Доступ
   ограничивать декоратором `role_required` из `core/decorators.py`; `admin`
   проходит везде. У каждой вьюхи должен быть декоратор доступа — вьюха без
   него открыта всем авторизованным.
3. Секреты — только через `.env`, никогда в коде и не в репозитории.
4. Шаблоны — Bootstrap 5 с боковой навигацией; интерфейс должен оставаться
   пригодным для телефона, а не только для ноутбука.
5. Миграции — в `core/migrations/`, создавать через `makemigrations`.
6. Файлы в `deploy/` и любые `.service` / `.timer` / `.conf` — только с
   переводами строк LF (закреплено в `.gitattributes`): systemd не выполнит
   юнит с CRLF.
7. В командах для пользователя — одна команда на блок. Многострочная вставка
   в терминал теряет части команд.
8. В шаблонах для комментариев использовать `{% comment %}`, а не `{# #}`:
   многострочный `{# #}` не вырезается и печатается на этикетке видимым
   текстом.
9. Служебные файлы должны присутствовать и обновляться вместе с версией:
   `start`, `setup_git`, `push_to_github`, `fix_git`, `update`,
   `update_version` (`.bat` и `.sh`), `lifteam_launcher.py`, `TZ.md`,
   `PROMPT.md`, `README.md`, `CHANGELOG.md`.
10. Файлы, добавленные владельцем проекта (логотипы, образцы документов,
    выгрузки), не удалять без разрешения.

## Запуск

Разработка — `python lifteam_launcher.py`: проверяет Python и зависимости,
создаёт базу, администратора и ячейки, запускает сервер.

Тесты — `python manage.py test`.

Резервные копии — `python manage.py backup_db`, восстановление —
`python manage.py restore_db`. На Raspberry Pi копии делает таймер systemd
(`deploy/lifteam-backup.timer`).

## Развёртывание

Полная установка на Raspberry Pi описана в `DEPLOY.md` — от записи системы на
носитель до удалённого доступа, резервного копирования и разбора неполадок.
Файлы служб — в `deploy/`.

Обновление на Pi: администратор нажимает кнопку в разделе «Обновление».
Приложение при этом **не получает прав root** — оно создаёт файл-заявку, а
работу выполняет служба systemd, реагирующая на его появление
(`deploy/lifteam-update.path`, `deploy/lifteam-update-runner.sh`). Это
разделение намеренное: иначе уязвимость в веб-приложении означала бы root на
машине. Не упрощать его.

## Этикетки

Формат — 43×25 мм, термопринтер. QR-коды содержат ссылки, а не текст:
`/p/<id>/` для детали, `/c/<id>/` для ячейки. Короткие пути — не украшение:
каждый лишний десяток символов увеличивает число модулей в коде и уменьшает
размер модуля при печати.

Проверенный на практике порог — не ниже ~3,5 точки принтера на модуль. При
29 модулях это даёт 13 мм; 9 мм (2,5 точки на модуль) на практике не
считывалось.

`LABEL_BASE_URL` в настройках задаёт основу ссылок. Нужен, когда печатают
через Tailscale, а сканируют телефоном в офисе: иначе в код попадёт адрес,
недоступный без VPN.
